@@ brief
- Tout moteur de recherche fait la même chose : il calcule un **score** `sim(question, document)` pour chaque document, trie, et renvoie les N meilleurs. Ce qui change d'un moteur à l'autre, c'est ce que calcule `sim`.
- 🔑 La recherche **lexicale** (ce module) compte les mots en commun. La recherche **sémantique** (module 2) compare le sens. « Can I still join the course? » et « Is it possible to enroll late? » veulent dire la même chose, mais n'ont presque aucun mot en commun.
- **minsearch** est un petit moteur en mémoire écrit par Alexey, le formateur. Il reprend les mots d'Elasticsearch : ce que tu apprends ici se transpose tel quel.
- 🔑 Deux sortes de champs. Les **champs texte** (`question`, `section`, `answer`) sont découpés en mots et classés. Les **champs mot-clé** (`course`) servent au filtrage exact, comme un `WHERE` en SQL.
- `boost_dict` donne plus de poids à un champ (`question` × 2, `section` × 0,5). `filter_dict` garde seulement un cours. `num_results` fixe le nombre de résultats.

@@ constraints
- `search(query, course="llm-zoomcamp", num_results=5, boost=None)` renvoie une liste de documents
- `boost=None` utilise `{"question": 2.0, "section": 0.5}`
- Un slug de cours inconnu lève une `ValueError` qui liste les cours valides
- Tu compares les questions du top 3 avec le boost par défaut et avec `{"question": 1.0}`, sur la même requête
- Tu trouves une requête qui **échoue** : la bonne entrée existe dans la FAQ, mais elle n'est pas dans le top 5

@@ guide
### 1. La liste des cours valides

Calcule-la une fois, à partir des documents : `COURSES = {doc["course"] for doc in documents}`. Un ensemble répond vite à « est-ce que ce slug existe ? ».

### 2. Le garde-fou

Au début de la fonction, si `course not in COURSES`, lève une erreur claire. Le message doit aider la personne à corriger : donne-lui la liste triée des cours.

### 3. La valeur par défaut

Ne mets jamais un dictionnaire comme valeur par défaut (`boost={...}`) : en Python, il est créé **une seule fois** et partagé entre tous les appels. On écrit `boost=None`, puis `if boost is None: boost = {...}` dans la fonction.

### 4. Comparer deux boosts

Pour une même requête, affiche `[d["question"] for d in search(q)][:3]` avec le boost par défaut, puis avec `boost={"question": 1.0}`. Toutes les requêtes ne bougent pas : essaie-en plusieurs. « Where do I submit my homework? » montre bien la différence.

### 5. Trouver un échec

Reprends l'exemple du cours : « Is it possible to enroll late? ». Cherche aussi une faute de frappe sur un nom d'outil (« Olama » au lieu de « Ollama »). Pour chaque échec, écris en commentaire **pourquoi** la recherche lexicale rate.

@@ hints
- `sorted(COURSES)` donne une liste triée, plus lisible dans un message d'erreur.
- Pour vérifier que l'entrée existe vraiment : `[d["question"] for d in documents if "join" in d["question"].lower() and d["course"] == "llm-zoomcamp"]`.
- Si ta requête « qui échoue » trouve quand même la bonne entrée, change un mot de plus : un seul mot commun peut suffire à faire remonter un document.

@@ solution
~~~python
from minsearch import Index

index = Index(
    text_fields=["question", "section", "answer"],
    keyword_fields=["course"]
)
index.fit(documents)

COURSES = {doc["course"] for doc in documents}
DEFAULT_BOOST = {"question": 2.0, "section": 0.5}


def search(query, course="llm-zoomcamp", num_results=5, boost=None):
    if course not in COURSES:
        raise ValueError(f"Cours inconnu : {course!r}. Cours valides : {sorted(COURSES)}")
    if boost is None:
        boost = DEFAULT_BOOST
    return index.search(
        query,
        boost_dict=boost,
        filter_dict={"course": course},
        num_results=num_results,
    )


# Comparer deux boosts sur la même requête
q = "Where do I submit my homework?"
print([d["question"] for d in search(q)][:3])
print([d["question"] for d in search(q, boost={"question": 1.0})][:3])
# Avec question × 2, « Where do I submit my capstone project? » passe en tête :
# les mots « where », « submit » et « my » sont dans sa question. Sans le boost, il sort du top 3.

# Un échec de la recherche lexicale
late = search("Is it possible to enroll late?")
print([d["question"] for d in late])
# → « I just discovered the course. Can I still join? » n'y est pas :
#   « enroll » et « late » n'apparaissent pas dans cette entrée, « join » et « still » oui.

# Le garde-fou
try:
    search("Can I join?", course="llm-zoomcap")
except ValueError as e:
    print(e)
~~~

Sur ma copie de la FAQ, « Is it possible to enroll late? » ne trouvait pas l'entrée « Can I still join? », et « How do I run Olama locally? » ratait les entrées sur Ollama. Tes résultats peuvent différer un peu si la FAQ a changé.

Fais deux fautes de frappe dans le filtre, l'une après l'autre, **directement** avec `index.search` (sans ta fonction) :

~~~python
index.search("Can I join?", filter_dict={"course": "llm-zoomcap"}, num_results=5)   # faute dans la valeur
index.search("Can I join?", filter_dict={"cours": "llm-zoomcamp"}, num_results=5)   # faute dans le nom du champ
~~~

Les deux fautes se comportent-elles de la même façon ? Laquelle est la plus dangereuse dans une application ?

@@ breakfix-hints
- Regarde ce que renvoie la première ligne : une erreur, ou autre chose ?
- Pour la deuxième, lis le message d'erreur jusqu'au bout : il te donne la liste des champs acceptés.
- Une erreur qui fait planter, on la voit tout de suite. Une erreur silencieuse, on la découvre quand un utilisateur se plaint.

@@ breakfix-answer
Elles ne se comportent **pas** pareil (minsearch 0.2.0) :

- faute dans la **valeur** (`"llm-zoomcap"`) : `index.search` renvoie `[]`, **sans erreur**. Aucun document n'a ce slug, donc le filtre ne garde rien ;
- faute dans le **nom du champ** (`"cours"`) : `FilterValidationError: Unknown filter field 'cours'. Valid fields are: ['course']`.

La plus dangereuse est la première. Dans le RAG, une liste vide donne un contexte vide, et le modèle répond « I don't know » à une question qui a pourtant une réponse dans la FAQ. Rien ne plante, rien ne prévient. C'est exactement pour ça que ta fonction vérifie le slug **avant** de chercher : on transforme une erreur silencieuse en erreur visible.
