@@ brief
- minsearch vit **en mémoire** : quand le programme s'arrête, l'index disparaît, et on réindexe à chaque démarrage. Avec une petite FAQ, ça prend moins d'une seconde. Avec des millions de documents, des minutes.
- 🔑 On **sépare l'ingestion de l'interrogation**. Un processus écrit les données dans un index **persistant**. Un autre le lit. Ils ne partagent que l'index.
- **sqlitesearch** a la même API que minsearch, mais il est rangé dans un fichier SQLite (`faq.db`), grâce à **FTS5**, la recherche plein texte intégrée à SQLite. SQLite est livré avec Python : rien à installer de plus.
- Le notebook d'ingestion ajoute les documents un par un avec `index.add(doc)`. Pendant ce temps, un autre notebook ouvre le même `faq.db` et voit `count()` grandir.
- `RAGBase` ne change pas : on lui passe `sqlite_index` au lieu de l'index minsearch. C'est le bénéfice de la leçon 8.

@@ predict
L'ingestion est terminée : `faq.db` contient les documents du cours LLM. Tu relances **toute** la cellule d'ingestion de la leçon, celle avec la boucle `index.add(doc)`. Que devient `count()` ? Et si tu remplaces la boucle par `index.fit(docs_llm)` ?

@@ predict-answer
Avec `add`, `count()` **double**. sqlitesearch ajoute sans vérifier si le document existe déjà. La recherche renvoie alors chaque réponse **deux fois** : le contexte du modèle contient des doublons, et tu paies deux fois les mêmes tokens.

Avec `fit` sur un index qui n'est pas vide, sqlitesearch refuse : `ValueError: Index already contains documents. Use clear() to reset the index or add() to append documents.`

Le notebook du cours n'est donc **pas idempotent** : on ne peut pas le relancer sans risque. Dans un vrai projet, l'ingestion tourne chaque nuit, plante parfois au milieu, et on la relance. Elle doit pouvoir tourner deux fois sans rien casser.

@@ guide
### 1. Les fichiers du cours

Copie `ingest.py` du cours à côté de `rag_helper.py` : `cp /workspaces/llm-zoomcamp/01-agentic-rag/code/ingest.py .`, puis `uv add sqlitesearch`.

### 2. Les options

`argparse` lit la ligne de commande. `nargs="+"` accepte un ou plusieurs mots : `--courses llm-zoomcamp data-engineering-zoomcamp`. `parser.error("...")` affiche ton message et arrête le script avec un code d'erreur.

### 3. L'idempotence

Deux façons de faire, choisis-en une et écris pourquoi dans un commentaire :

- **vider puis reconstruire** : `index.clear()` si `count()` n'est pas nul, puis `index.fit(docs)` ;
- **ajouter seulement ce qui manque** : comparer les `id` déjà présents. Plus rapide pour une grosse base, plus compliqué.

Pour une FAQ de quelques centaines de documents, la première suffit.

### 4. Un chemin fiable

`db_path="faq.db"` est **relatif** : il dépend du dossier où tu te trouves quand tu lances le script. `Path(__file__).resolve().parent / "faq.db"` désigne toujours le dossier du script.

### 5. Mesurer

`time.perf_counter()` au début et à la fin donne la durée. `collections.Counter` compte les documents par cours.

@@ hints
- Lance le script **deux fois** à la suite et compare les deux lignes « après ».
- Si `fit` lève `Index already contains documents`, c'est que `clear()` n'a pas été appelé avant.
- `index.close()` à la fin : sur un vrai serveur, une connexion SQLite oubliée peut bloquer le fichier pour les autres processus.
- Bonus de pro : construire l'index dans un fichier temporaire, puis le mettre à la place de l'ancien avec `os.replace`. Pendant l'ingestion, les lecteurs gardent l'ancien index complet au lieu d'un index à moitié vide.

@@ solution
~~~python
"""Remplit faq.db avec la FAQ. Relançable sans risque : l'index est vidé puis reconstruit."""
import argparse
import time
from collections import Counter
from pathlib import Path

from sqlitesearch import TextSearchIndex

from ingest import load_faq_data

# Le chemin est calculé à partir du fichier du script, pas du dossier d'où on le lance.
DB_PATH = Path(__file__).resolve().parent / "faq.db"


def main():
    parser = argparse.ArgumentParser(description="Ingère la FAQ dans un index SQLite persistant.")
    parser.add_argument("--courses", nargs="+", default=["llm-zoomcamp"],
                        help="slugs des cours à ingérer (par défaut : llm-zoomcamp)")
    parser.add_argument("--db", default=str(DB_PATH), help="chemin du fichier de l'index")
    args = parser.parse_args()

    start = time.perf_counter()
    documents = load_faq_data()
    known = {doc["course"] for doc in documents}
    unknown = set(args.courses) - known
    if unknown:
        parser.error(f"cours inconnus : {sorted(unknown)}. Cours valides : {sorted(known)}")

    docs = [doc for doc in documents if doc["course"] in args.courses]

    index = TextSearchIndex(
        text_fields=["question", "section", "answer"],
        keyword_fields=["course"],
        db_path=args.db,
    )
    before = index.count()
    if before:
        index.clear()          # sinon fit() refuse, et add() créerait des doublons
    index.fit(docs)
    after = index.count()
    index.close()

    print(f"Index : {args.db}")
    print(f"Avant : {before} documents, après : {after} documents")
    for course, n in sorted(Counter(doc["course"] for doc in docs).items()):
        print(f"  {course} : {n}")
    print(f"Durée : {time.perf_counter() - start:.1f} s")


if __name__ == "__main__":
    main()
~~~

@@ cles
- L'idempotence | idempotent data pipeline | Un job qu'on peut relancer sans risque, c'est un job qu'on peut planifier et réparer sans peur.
- SQLite FTS5 | sqlite fts5 full text search | Un vrai moteur de recherche plein texte, déjà livré avec Python.
- Les chemins relatifs et absolus | python pathlib __file__ relative path | Le dossier courant change selon qui lance le programme : un chemin relatif est une bombe à retardement.
- Le remplacement atomique | atomic file replace os.replace | Les lecteurs voient l'ancien index ou le nouveau, jamais un index à moitié construit.
