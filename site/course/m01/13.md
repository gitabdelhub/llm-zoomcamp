@@ brief
- Dans le RAG, le modèle est un **passager** : il ne voit jamais les mauvais résultats de la recherche, il ne peut pas réessayer. Avec un agent, il devient le **conducteur**.
- 🔑 L'**appel de fonctions** (function calling) : on décrit un outil au modèle avec un **schéma JSON** (nom, description, paramètres). Le modèle ne voit jamais ton code Python, seulement ce schéma. Le champ le plus important est `description` : c'est en le lisant que le modèle décide d'appeler l'outil.
- Avec `tools=[search_tool]`, la réponse ne contient plus un message mais un `function_call` : le modèle **demande** qu'on lance `search` avec ses arguments. Il réécrit souvent la question en mots-clés.
- On exécute la fonction **nous-mêmes**, puis on renvoie au modèle tout l'historique : la question, son `function_call`, et le résultat dans un `function_call_output` avec le même `call_id`.
- 🔑 Les LLM sont **sans état** (stateless) : leur seule mémoire est la liste qu'on envoie dans `input`. Deux appels au lieu d'un, et le deuxième renvoie tout l'historique : un agent coûte plus cher qu'un RAG.

@@ predict
Tu envoies la question avec `tools=[search_tool]`. Le modèle décide d'appeler `search`. Que vaut `response.output_text` dans ce cas ?

@@ predict-answer
Une **chaîne vide** : `""`. `output_text` ne rassemble que le texte des éléments de type `message`. Ici, `response.output` contient seulement un élément `function_call` : le modèle n'a encore rien répondu, il attend le résultat de l'outil.

C'est un piège fréquent : un programme qui affiche `response.output_text` sans regarder `response.output` croit que le modèle a répondu « rien ». Avec des outils, on regarde **toujours** `response.output` d'abord, et le type de chaque élément.

@@ practice
Donne à ton assistant un outil qui sait chercher dans **tous** les cours, et laisse le modèle choisir lequel. Tu fais l'aller-retour complet à la main et tu comptes ce qu'il coûte.

@@ constraints
- `search(query, course)` cherche dans le cours donné et lève une `ValueError` si le slug est inconnu
- Le schéma de l'outil a deux paramètres obligatoires : `query` et `course`, avec un `enum` qui liste les slugs des cours
- `ask_with_tool(question)` fait les deux appels et exécute **chaque** `function_call` de la réponse, chacun avec son `call_id`
- Elle affiche les arguments choisis par le modèle, et renvoie la réponse avec l'`usage` des deux appels
- 3 questions testées : une avec une faute de frappe (« Olama »), une sur le cours DE, une en français

@@ guide
### 1. Un enum dans le schéma

Dans un schéma JSON, `"enum": [...]` limite un paramètre à une liste de valeurs. Le modèle ne pourra pas inventer `llm-zoomcap` : c'est le garde-fou de la leçon 5, mais côté modèle. Calcule la liste à partir des documents, triée.

### 2. Les descriptions

Écris-les pour le modèle, comme une consigne : quand appeler l'outil, et comment remplir chaque paramètre. Par exemple, pour `query` : « Search keywords in English, with typos fixed. » Pour `course` : quel cours choisir si l'utilisateur ne dit rien.

### 3. Lire la réponse

`response.output` est une liste. Garde les éléments dont `item.type == "function_call"`. S'il n'y en a aucun, le modèle a répondu directement : renvoie `response.output_text`.

### 4. Exécuter et renvoyer

Pour chaque appel : `args = json.loads(call.arguments)`, puis `search(**args)`. Ajoute d'abord `response.output` à l'historique avec `messages.extend(...)`, puis un `function_call_output` par appel.

### 5. Compter

Garde `usage` des **deux** appels. Additionne les tokens d'entrée : tu verras que le deuxième appel pèse beaucoup plus lourd, parce qu'il contient les 5 résultats en JSON.

@@ hints
- `search(**args)` déballe le dictionnaire : `{"query": "x", "course": "y"}` devient `search(query="x", course="y")`. Les noms du schéma doivent donc être **exactement** ceux de ta fonction.
- Pour la question en français, regarde l'argument `query` : le modèle le traduit-il en anglais ? Repense à la leçon 6, où la recherche ne trouvait rien en français.
- `json.dumps(results)` transforme la liste de documents en texte : la sortie d'un outil est toujours une chaîne.

@@ solution
~~~python
import json

COURSES = sorted({doc["course"] for doc in documents})


def search(query, course):
    if course not in COURSES:
        raise ValueError(f"Cours inconnu : {course!r}")
    return index.search(
        query,
        num_results=5,
        boost_dict={"question": 3.0, "section": 0.5},
        filter_dict={"course": course},
    )


search_tool = {
    "type": "function",
    "name": "search",
    "description": "Search the FAQ of the DataTalksClub courses. Call it before answering any question about a course.",
    "parameters": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search keywords in English, with typos fixed.",
            },
            "course": {
                "type": "string",
                "enum": COURSES,
                "description": "The course the question is about. Use llm-zoomcamp if the user does not say.",
            },
        },
        "required": ["query", "course"],
        "additionalProperties": False,
    },
}


def ask_with_tool(question):
    messages = [{"role": "user", "content": question}]
    r1 = openai_client.responses.create(model="gpt-5.4-mini", input=messages, tools=[search_tool])

    calls = [item for item in r1.output if item.type == "function_call"]
    if not calls:                      # le modèle a répondu sans chercher
        return r1.output_text, [r1.usage]

    messages.extend(r1.output)         # le modèle doit revoir ses propres appels
    for call in calls:
        args = json.loads(call.arguments)
        print("→", call.name, args)
        results = search(**args)
        messages.append({
            "type": "function_call_output",
            "call_id": call.call_id,
            "output": json.dumps(results),
        })

    r2 = openai_client.responses.create(model="gpt-5.4-mini", input=messages, tools=[search_tool])
    return r2.output_text, [r1.usage, r2.usage]


for q in [
    "How do I run Olama locally?",
    "Where do I submit my homework for the data engineering course?",
    "Je viens de découvrir le cours, est-ce que je peux encore m'inscrire ?",
]:
    answer, usages = ask_with_tool(q)
    print(answer)
    print("tokens d'entrée par appel :", [u.input_tokens for u in usages])
    print()
~~~

@@ breakfix-hints
- L'API reçoit le résultat d'un outil avec un `call_id`. Peut-elle retrouver l'appel qui correspond ?
- Rappelle-toi : le modèle n'a aucune mémoire entre deux appels. Il ne sait que ce qu'il y a dans `input`.
- L'erreur ne vient pas de Python, mais du serveur d'OpenAI : regarde le code HTTP.

@@ breakfix-answer
L'API refuse la requête avec une erreur **400** (`openai.BadRequestError`). Le message dit, en substance, qu'aucun appel de fonction ne correspond au `call_id` du `function_call_output`. Je n'ai pas pu lancer ce test ici, sans clé : le texte exact peut varier, le code 400 et le sens non.

La cause : le modèle est **sans état**. Au deuxième appel, il ne se souvient pas avoir demandé `search`. Un résultat d'outil qui arrive sans l'appel qui le précède est une conversation incohérente, et l'API la rejette.

La règle à retenir : l'historique contient, dans l'ordre, la question, **puis** les `function_call` du modèle, **puis** un `function_call_output` par appel, avec le même `call_id`.

@@ cles
- L'appel de fonctions (function calling) | openai function calling responses api | Le mécanisme qui transforme un modèle qui parle en un modèle qui agit.
- JSON Schema | json schema enum required additionalProperties | Le langage qui décrit les outils à tous les modèles, d'OpenAI comme d'Anthropic ou de Google.
- Les LLM sans état | LLM stateless conversation history | La mémoire d'un chatbot, c'est la liste que tu renvoies : c'est aussi ce qui fait grimper le prix.
- La description d'un outil | tool description best practices LLM agents | Le modèle choisit ses outils en lisant leurs descriptions : une bonne description vaut mieux que dix lignes de code.
