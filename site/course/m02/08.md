@@ brief
- Beaucoup de vraies bases savent faire de la recherche vectorielle (Elasticsearch, Qdrant, Chroma…). Le cours prend **Postgres**, avec l'extension **pgvector** : la base la plus courante en entreprise, et celle de ton Zoomcamp DE.
- L'image Docker `pgvector/pgvector:pg17` contient l'extension ; `CREATE EXTENSION IF NOT EXISTS vector` l'active dans la base. On gagne un type de colonne, `vector(384)`, et des opérateurs de distance.
- On se connecte avec **psycopg 3** : `conn.execute(...)` directement, sans curseur. Le vecteur part en texte (`"[0.1,0.2,...]"`), et `%s::vector` le reconvertit.
- 🔑 `<=>` calcule la **distance** cosinus, soit `1 - similarité`. On trie donc par ordre **croissant** : la plus petite distance d'abord.
- Le filtre par cours, c'est un simple `WHERE course = %s` : du SQL ordinaire.
- `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)` crée un index **HNSW** pour passer en recherche approximative sur de gros volumes. `vector_cosine_ops` doit correspondre à l'opérateur de la requête, ici `<=>`.

@@ predict
Tu as indexé les 1470 documents et créé l'index HNSW de la leçon. Tu lances `EXPLAIN` sur la requête de recherche, pour voir comment Postgres l'exécute. Utilise-t-il ton index ?

@@ predict-answer
**Non.** Sur ma table de 1470 lignes, le plan est un `Seq Scan on documents` suivi d'un `Sort` : Postgres lit toute la table et trie, exactement comme `X.dot(v)` en numpy. Même après `ANALYZE`, le résultat est le même.

Postgres choisit son plan d'après une estimation du **coût**. Pour 1470 lignes, tout lire prend environ 1 milliseconde ; parcourir le graphe HNSW coûterait plus. L'index n'est utilisé que si on interdit la lecture complète (`SET enable_seqscan = off`), ce qui sert seulement à vérifier qu'il existe.

Créer un index ne garantit pas qu'il sera utilisé. `EXPLAIN` (et `EXPLAIN ANALYZE`, qui exécute vraiment la requête) est le seul moyen de le savoir. C'est aussi vrai pour un index ordinaire sur une colonne de texte.

@@ practice
Passe d'une commande `docker run` et d'un notebook à une installation qu'on peut relancer : un fichier Compose, et un script d'ingestion rapide et sans doublons.

@@ constraints
- Un `docker-compose.yaml` avec le service pgvector, un **volume nommé** et un healthcheck
- Un script `ingest_pg.py` qui crée la table si elle n'existe pas, avec l'`id` de la FAQ comme clé primaire
- Les insertions se font avec `executemany`, en une seule transaction
- Relancé, le script ne crée aucun doublon : le compte reste à 1470
- Après `docker compose down` puis `docker compose up -d`, les données sont toujours là
- Le plan `EXPLAIN ANALYZE` de ta requête filtrée par cours, avec une phrase pour dire si l'index est utilisé

@@ guide
### 1. Le fichier Compose

Reprends les paramètres du `docker run` de la leçon : l'image, les trois variables `POSTGRES_*`, le port, le volume. Le volume se déclare deux fois : dans le service (`pgvector_data:/var/lib/postgresql/data`) et en bas du fichier, dans `volumes:`.

### 2. Attendre que Postgres soit prêt

Un healthcheck avec `pg_isready -U user -d faq`, puis `docker compose up -d --wait` : la commande rend la main quand la base répond.

### 3. La clé primaire

La leçon utilise `id SERIAL` : un numéro créé par Postgres. Relancer le script ajoute alors 1470 lignes de plus. Avec `id TEXT PRIMARY KEY` (l'`id` de la FAQ) et `ON CONFLICT (id) DO NOTHING`, une ligne déjà présente est ignorée.

### 4. executemany

`with conn.cursor() as cur: cur.executemany(sql, rows)`, où `rows` est une liste de tuples. Un seul `commit` à la fin : soit tout passe, soit rien.

### 5. Le plan

`conn.execute("EXPLAIN ANALYZE SELECT ...", params).fetchall()` renvoie une ligne de texte par étape du plan. Cherche `Seq Scan` ou `Index Scan`.

@@ hints
- `psycopg.connect(...)` utilisé avec `with` fait un `commit` automatique à la sortie du bloc (ou un `rollback` en cas d'erreur).
- Sur ma machine, la boucle `conn.execute` de la leçon prend 0,9 s pour 1470 lignes, et `executemany` 0,5 s. L'écart grandit avec le volume et la distance au serveur : chaque `execute` est un aller-retour réseau.
- `CREATE INDEX IF NOT EXISTS nom ON ...` exige un nom d'index : c'est ce qui permet de relancer le script.
- `docker compose down -v` supprime **aussi** le volume, donc les données. Sans `-v`, elles restent.

~~~python
# ingest_pg.py
import time

import numpy as np
import psycopg

from ingest import load_faq_data

PG_URL = "postgresql://user:pswd@localhost:5432/faq"

documents = load_faq_data()
X = np.load("X.npy")   # leçon 3 : vérifie que ids.json correspond, sinon recalcule


def vec_to_str(vector):
    return "[" + ",".join(str(x) for x in vector) + "]"


with psycopg.connect(PG_URL) as conn:
    conn.execute("CREATE EXTENSION IF NOT EXISTS vector")
    conn.execute("""
        CREATE TABLE IF NOT EXISTS documents (
            id TEXT PRIMARY KEY,
            course TEXT,
            section TEXT,
            question TEXT,
            answer TEXT,
            embedding vector(384)
        )
    """)
    rows = [(d["id"], d["course"], d["section"], d["question"], d["answer"], vec_to_str(v))
            for d, v in zip(documents, X)]
    start = time.perf_counter()
    with conn.cursor() as cur:
        cur.executemany("""
            INSERT INTO documents (id, course, section, question, answer, embedding)
            VALUES (%s, %s, %s, %s, %s, %s::vector)
            ON CONFLICT (id) DO NOTHING
        """, rows)
    conn.execute("""
        CREATE INDEX IF NOT EXISTS documents_embedding_idx
        ON documents USING hnsw (embedding vector_cosine_ops)
    """)
    n = conn.execute("SELECT count(*) FROM documents").fetchone()[0]
    print(f"{n} documents dans la table ({time.perf_counter() - start:.1f} s)")
~~~

@@ breakfix
Tu décides d'essayer un modèle d'embeddings plus gros, qui produit des vecteurs de **768** nombres, mais tu gardes ta table. Simule-le : cherche avec `vec_to_str(np.zeros(768))` à la place du vecteur de la question. Puis essaie d'**insérer** une ligne avec ce vecteur. Les deux erreurs sont-elles les mêmes ?

@@ breakfix-hints
- La colonne a été créée en `vector(384)` : que vérifie Postgres à l'insertion ?
- Et pour une recherche, quel calcul est impossible entre deux vecteurs de tailles différentes ?
- Après une erreur, psycopg refuse toute requête suivante sur la même connexion tant que tu n'as pas fait `conn.rollback()`.

@@ breakfix-answer
Deux erreurs différentes, toutes les deux claires :

- la recherche : `different vector dimensions 384 and 768` ;
- l'insertion : `expected 384 dimensions, not 768`.

C'est l'avantage d'une colonne **typée** : Postgres refuse les vecteurs de la mauvaise taille. numpy, lui, n'aurait rien dit si tu avais mélangé deux matrices de même taille venant de deux modèles différents. Ce cas-là, aucune base ne le détecte : deux modèles différents en 384 dimensions donnent des vecteurs de même taille, mais sans rapport entre eux.

La règle : changer de modèle, c'est **réindexer tous les documents**. Le nom du modèle fait partie du contrat entre l'ingestion et l'application, comme à la leçon 7. Et après une erreur, n'oublie pas `conn.rollback()` : sinon psycopg répond `current transaction is aborted` à toutes les requêtes suivantes.
