@@ brief
- En production, on veut peu de dépendances et une image légère. sentence-transformers tire PyTorch et les bibliothèques NVIDIA : **4,8 Go** et 58 paquets dans la mesure du cours. **ONNX Runtime** fait tourner le même modèle avec **147 Mo** et 27 paquets, 33 fois moins.
- ONNX est un format standard pour les réseaux de neurones. On télécharge souvent une version ONNX déjà publiée, ici celle de `Xenova/all-MiniLM-L6-v2`, avec `download.py`.
- Un projet séparé : `uv add onnxruntime tokenizers numpy tqdm minsearch`, et `huggingface-hub` en dépendance de développement, seulement pour télécharger.
- La classe `Embedder` (`embedder.py`) fait à la main ce que sentence-transformers cachait : **découper** le texte en tokens, **exécuter** le modèle, faire la **moyenne** des vecteurs de tokens (pondérée par le masque d'attention), puis **normaliser**.
- 🔑 Même interface qu'avant : `embed.encode(texte)` et `embed.encode_batch(textes)`. Le reste du code ne change pas.

@@ guide
### 1. Regarder la coupe

`embed.tokenizer.truncation` affiche la configuration de coupe du `tokenizer.json` : un dictionnaire avec `max_length`, ou `None` si le texte n'est jamais coupé. Note la valeur **avant** d'encoder la FAQ.

### 2. Comparer à sentence-transformers

Ton `X.npy` et ton `ids.json` de la leçon 3 sont dans `../module-02/`. Vérifie d'abord que les `id` correspondent aux documents chargés. Puis, pour chaque ligne, le produit scalaire entre le vecteur de sentence-transformers et le vecteur ONNX : `(X_st * X_onnx).sum(axis=1)`. 1 veut dire identique.

### 3. Régler la coupe

sentence-transformers coupe à `model.max_seq_length`, soit 256 pour ce modèle. Le tokenizer a une méthode `enable_truncation(max_length)`. Appelle-la sur `embed.tokenizer`, puis réencode.

### 4. Les tailles

`du -sh .venv` dans les deux projets.

@@ hints
- Si l'encodage plante avec `Attempting to broadcast an axis…`, c'est que la coupe vaut `None` : un texte de plus de 512 tokens dépasse ce que le modèle sait lire. C'est l'étape 3 qui répare.
- Si presque la moitié des documents diffèrent, c'est que la coupe est plus courte que 256 : seuls les textes courts donnent le même vecteur.
- `encode_batch` appelle `enable_padding()` à chaque fois, mais ne touche pas à la coupe : un `enable_truncation` fait une fois reste actif.
- Ton projet de la leçon 2 utilise l'index PyTorch CPU : l'écart de taille sera plus petit que les 33 fois de la leçon, qui comptent la version CUDA.

@@ solution
~~~python
import json
from pathlib import Path

import numpy as np
from embedder import Embedder
from ingest import load_faq_data

documents = load_faq_data()
texts = [d["question"] + " " + d["answer"] for d in documents]

X_st = np.load("../module-02/X.npy")
ids_st = json.loads(Path("../module-02/ids.json").read_text())
assert ids_st == [d["id"] for d in documents], "La FAQ a changé : recalcule X.npy (leçon 3)"

embed = Embedder()
print("Coupe du tokenizer :", embed.tokenizer.truncation)


def embed_all():
    return np.vstack([embed.encode_batch(texts[i:i + 50]) for i in range(0, len(texts), 50)])


def compare(X_onnx):
    sim = (X_st * X_onnx).sum(axis=1)
    print(f"{(sim < 0.999).sum()} documents différents, similarité minimale {sim.min():.3f}")


try:
    compare(embed_all())
except Exception as e:
    print("L'encodage plante :", str(e)[:100])

embed.tokenizer.enable_truncation(256)   # la coupe de sentence-transformers
compare(embed_all())
~~~

Avec la copie du modèle que j'ai pu tester, la première comparaison affiche 793 documents différents, et la seconde **0**, avec une similarité minimale de 1,000. Ta première ligne dépend de ce que contient le `tokenizer.json` de Xenova : c'est précisément ce que tu vérifies.
