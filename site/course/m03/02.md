# Le contexte : pourquoi un chatbot écrit du vieil Airflow

Commençons par voir ce qui se passe quand un modèle manque de contexte.

## L'expérience

1. Ouvre ChatGPT (ou un autre chatbot) dans une fenêtre de navigation **privée**, pour qu'il n'ait aucun historique de tes conversations.
2. Demande-lui :

   ```text
   Write an Airflow DAG that loads the DataTalksClub FAQ into a pgvector table every day.
   ```

3. Regarde le code. Très souvent, tu y trouveras des lignes comme celles-ci :

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.utils.dates import days_ago

with DAG(
    dag_id="faq_ingest",
    schedule_interval="@daily",
    start_date=days_ago(1),
) as dag:
    PythonOperator(task_id="load_faq", python_callable=load_faq, provide_context=True)
```

C'est du code **Airflow 2**. Airflow 3 est sorti en avril 2025, et la plupart du code Airflow publié sur Internet, celui sur lequel les modèles ont appris, date d'avant.

## Pourquoi ça arrive

Un modèle de langage ne connaît que ce qu'il a vu pendant son entraînement, jusqu'à une certaine date. Il ne sait pas qu'une bibliothèque a renommé un paramètre, qu'une fonction a disparu, ou que ton équipe a ses propres conventions. Et quand il ne sait pas, il ne le dit pas : il produit le code **le plus probable**, c'est-à-dire le plus fréquent dans ce qu'il a lu.

C'est exactement le problème du RAG du module 1, vu de l'autre côté : sans les bons documents dans le prompt, le modèle répond avec ce qu'il croit savoir.

## 🔑 Ce qui a changé entre Airflow 2 et Airflow 3

J'ai lancé le DAG ci-dessus dans un vrai Airflow 3.3.2. Voici ce que chaque ligne devient :

| Ce que le chatbot écrit (Airflow 2) | Dans Airflow 3.3.2 | Ce qu'il faut écrire |
| --- | --- | --- |
| `from airflow.utils.dates import days_ago` | `ImportError` : la fonction n'existe plus | `start_date=datetime(2026, 11, 1)` |
| `schedule_interval="@daily"` | `TypeError` : paramètre inconnu | `schedule="@daily"` |
| `provide_context=True` | `TypeError` : argument invalide | rien : le contexte est toujours disponible |
| `from airflow.operators.python import PythonOperator` | marche, avec un avertissement `DeprecatedImportWarning` | `from airflow.sdk import dag, task`, et `@task` |
| `def ma_tache(execution_date=None)` | **aucune erreur**, mais la valeur vaut `None` | `logical_date` ou `ds` |

La dernière ligne est la plus dangereuse : rien ne plante, mais ton code reçoit `None` au lieu d'une date.

## Le contexte change tout

Sans contexte, un modèle produit du code périmé qu'il faut corriger ligne à ligne. Avec le bon contexte (la version, les imports à utiliser, ce qui est interdit, tes connexions et tes conventions), il produit du code qui marche du premier coup, ou presque. Le même principe vaut pour écrire du code et pour répondre à une question sur tes données : **le modèle ne travaille qu'avec ce qu'on lui donne**.

À la leçon 4, tu donneras ce contexte à un assistant une fois pour toutes, dans ton projet.

@@ brief
- Un modèle ne connaît que ses données d'entraînement. Sans contexte, il écrit le code **le plus fréquent** qu'il a lu, pas le plus récent : pour Airflow, du code Airflow 2.
- Dans Airflow 3.3.2 : `days_ago` n'existe plus (`ImportError`), `schedule_interval` devient `schedule` (`TypeError`), `provide_context` a disparu (`TypeError`), et `airflow.operators.python` marche encore avec un avertissement.
- 🔑 Le piège silencieux : un paramètre `execution_date` reçoit `None`, sans aucune erreur. Le nom actuel est `logical_date`.
- Le remède est le même que pour le RAG : **donner le contexte** au modèle, ici la version, les imports et tes conventions.

@@ declic
- [01-03] C'est le RAG du module 1, appliqué au code : sans les bons documents dans le prompt, le modèle répond avec ce qu'il croit savoir.
- [DE:02-03] Ton premier DAG du Zoomcamp DE était déjà en Airflow 3, avec `from airflow.sdk import dag, task`. Tu sais donc repérer du code Airflow 2 au premier coup d'œil.

@@ predict
Tu colles ce DAG du chatbot, tel quel, dans le dossier `dags/` d'Airflow 3.3.2, puis tu lances `airflow dags list-import-errors`. Combien d'erreurs Airflow affiche-t-il pour ce fichier ? Et une fois la première corrigée ?

@@ predict-answer
**Une seule à la fois.** Sur Airflow 3.3.2, j'ai obtenu trois erreurs différentes, l'une après l'autre :

1. `ImportError: cannot import name 'days_ago' from 'airflow.utils.dates'` ;
2. une fois `days_ago` remplacé : `TypeError: DAG.__init__() got an unexpected keyword argument 'schedule_interval'` ;
3. une fois `schedule` corrigé : `TypeError: Invalid arguments were passed to PythonOperator (task_id: load_faq)`, à cause de `provide_context`.

Python s'arrête à la **première** erreur d'un fichier. Tu ne vois donc jamais la liste complète : il faut corriger, relancer, corriger encore. C'est pour ça qu'on veut une boucle « générer, importer, lire l'erreur » la plus courte possible, et un contexte qui évite ces erreurs dès le départ.

@@ practice
Écris le **contexte** qui manque au chatbot, puis mesure ce qu'il change : le même prompt, avec et sans ton contexte, et le nombre d'erreurs à l'import de chaque version.

@@ constraints
- Un fichier `CONTEXT.md` dans `mon-travail/module-03/`, de 30 lignes au plus : la version d'Airflow, les imports à utiliser, ce qui est interdit, ta connexion `pgvector`, tes dossiers
- Deux fichiers dans `dags/` : `faq_sans_contexte.py` (le prompt seul) et `faq_avec_contexte.py` (ton `CONTEXT.md` collé avant le même prompt), tous les deux dans une **nouvelle** conversation privée
- Pour chacun, le nombre de corrections nécessaires avant que `airflow dags list-import-errors` ne dise plus rien
- Le paramètre `execution_date` n'apparaît dans aucun des deux fichiers finaux

@@ guide
### 1. Le contenu du contexte

Pense à ce que tu dirais à un collègue qui arrive dans le projet : quelle version, comment on écrit un DAG chez nous, ce qu'on n'utilise plus. Le tableau de la leçon est une bonne base pour la partie « interdit ».

### 2. Une conversation neuve à chaque fois

Le chatbot garde ce que tu lui as dit dans la même conversation. Pour une comparaison honnête, ouvre une nouvelle fenêtre privée pour chaque version.

### 3. Compter les corrections

Copie chaque fichier dans `dags/`. Tant que `airflow dags list-import-errors` montre ton fichier, corrige l'erreur affichée et relance. Note le nombre de tours. Si ton Airflow n'est pas encore installé, fais cette partie après la leçon 3.

### 4. Les erreurs qui ne s'affichent pas

Cherche `execution_date`, `days_ago` et `schedule_interval` dans les deux fichiers avec Ctrl + F. Le premier ne provoque aucune erreur à l'import.

@@ hints
- Des imports précis valent mieux qu'une consigne vague : « utilise `from airflow.sdk import dag, task, Param, Asset, Connection` » marche mieux que « utilise Airflow 3 ».
- Mets aussi un mini-exemple de DAG à toi, de 10 lignes : un modèle imite très bien un exemple.
- Si les deux versions marchent du premier coup, ton chatbot a peut-être appris Airflow 3 depuis. Regarde alors les détails : `retries`, `catchup`, le nom de la connexion. Le contexte sert aussi à faire respecter **tes** conventions.

@@ solution
Mon `CONTEXT.md` :

~~~markdown
# Contexte du projet : l'assistant de la FAQ, orchestré par Airflow

- Airflow **3.3.2**, dans Docker Compose, LocalExecutor. Python 3.12.
- Les DAG s'écrivent avec le Task SDK : `from airflow.sdk import dag, task, Param, Asset, Connection`.
- Chaque DAG : `start_date=datetime(2026, 11, 1)`, `catchup=False`, `schedule=` (jamais `schedule_interval`).
- Les dates d'exécution : `logical_date` ou `ds` dans la signature de la tâche.
- Interdit (Airflow 2) : `days_ago`, `schedule_interval`, `provide_context`, `execution_date`, `airflow.operators.python`.
- Postgres avec pgvector : la connexion Airflow `pgvector`, lue avec `Connection.get("pgvector").get_uri()` et psycopg 3.
- Table `documents` : id TEXT PRIMARY KEY, course, section, question, answer, embedding vector(384).
- Embeddings : la classe `Embedder` de `dags/embedder.py` (ONNX, all-MiniLM-L6-v2), `enable_truncation(256)`.
- La clé OpenAI vient de la variable d'environnement `OPENAI_API_KEY`. Jamais de clé dans le code.
- Les tâches qui appellent une API : `retries=3`, `retry_exponential_backoff=True`.

Exemple de DAG du projet :

```python
from datetime import datetime
from airflow.sdk import dag, task

@dag(schedule="@daily", start_date=datetime(2026, 11, 1), catchup=False)
def exemple():
    @task(retries=3)
    def extract(ds=None):
        return f"/opt/airflow/data/faq_{ds}.json"
    extract()

exemple()
```
~~~

Je n'ai pas pu interroger de chatbot depuis mon environnement : je ne peux pas te dire combien d'erreurs tu obtiendras. Ce que j'ai vérifié, c'est que chaque règle de ce contexte correspond à ce qu'accepte Airflow 3.3.2.

@@ breakfix
Un chatbot t'a donné cette tâche, et elle tourne sans erreur. Mets-la dans un DAG, lance-le avec `airflow dags test`, puis regarde le chemin affiché.

~~~python
@task
def extract(execution_date=None):
    path = f"/opt/airflow/data/faq_{execution_date}.json"
    print(path)
    return path
~~~

Qu'affiche-t-elle, et pourquoi ?

@@ breakfix-hints
- Airflow remplit les paramètres d'une tâche `@task` avec les clés du **contexte** qui portent le même nom.
- Ajoute `**context` à la signature et affiche `"execution_date" in context`.
- Un paramètre avec une valeur par défaut ne provoque jamais d'erreur quand Airflow ne le remplit pas.

@@ breakfix-answer
Sur Airflow 3.3.2, la tâche affiche `None`, sans erreur ni avertissement. `"execution_date" in context` vaut `False` : la clé a été **supprimée** dans Airflow 3 (elle s'appelle `logical_date`), et un paramètre absent du contexte garde sa valeur par défaut.

C'est le pire type de bug : le DAG est vert, les fichiers s'appellent `faq_None.json`, et chaque jour écrase le précédent. Un code généré se **vérifie**, même quand il marche : regarde ce qu'il produit, pas seulement s'il plante. Remplace par `logical_date=None` ou `ds=None`.

@@ explain
Pourquoi un modèle écrit-il du code Airflow 2 alors qu'Airflow 3 existe ? Et qu'est-ce qui rend l'erreur d'`execution_date` plus dangereuse que celle de `schedule_interval` ?
