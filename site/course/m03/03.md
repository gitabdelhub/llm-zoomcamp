Tu as installé Airflow 3.3.2 avec Docker Compose au Zoomcamp DE : le compose officiel, allégé avec le **LocalExecutor**. On repart de là, dans ton fork du LLM Zoomcamp, avec quatre ajouts pour ce module.

## Ce qu'on ajoute au compose du Zoomcamp DE

| Ajout | Pourquoi |
| --- | --- |
| Une **image à toi**, construite depuis un `Dockerfile` | Les tâches ont besoin d'`openai`, `onnxruntime`, `tokenizers`, `psycopg` et `minsearch`, absents de l'image officielle |
| Un service **pgvector** | La base des vecteurs du module 2, à côté de la base d'Airflow (jamais dedans) |

## 🔑 Une image construite, pas `_PIP_ADDITIONAL_REQUIREMENTS`

Le compose officiel propose une variable `_PIP_ADDITIONAL_REQUIREMENTS` qui installe des paquets au démarrage de **chaque** conteneur. Ses commentaires le disent eux-mêmes : à n'utiliser que pour un essai rapide. Chaque redémarrage réinstalle tout, et une version qui change en ligne peut casser ton Airflow du jour au lendemain. On construit donc une image une fois :

```dockerfile
FROM apache/airflow:3.3.2
COPY requirements.txt /requirements.txt
RUN pip install --no-cache-dir "apache-airflow==${AIRFLOW_VERSION}" -r /requirements.txt
```

`"apache-airflow==${AIRFLOW_VERSION}"` dans la même commande empêche pip de changer la version d'Airflow pour satisfaire une autre bibliothèque. C'est la méthode recommandée par la documentation d'Airflow.

Dans le compose, la ligne `image:` du bloc `x-airflow-common` est remplacée par `build: .` : `docker compose build` construit l'image à partir du `Dockerfile` du dossier.

## 🔑 Les secrets : des variables d'environnement

Kestra lit ses secrets dans des variables `SECRET_...` encodées en base64. Airflow a son propre mécanisme, plus simple : toute variable d'environnement `AIRFLOW_CONN_<NOM>` **est** une connexion, et toute variable `AIRFLOW_VAR_<NOM>` **est** une variable Airflow. Elles ne sont jamais enregistrées dans la base de métadonnées : `airflow variables list` ne les montre même pas.

Pour la clé OpenAI, c'est encore plus direct : ton secret Codespaces `OPENAI_API_KEY` existe déjà dans le terminal de ton Codespace. Une ligne du compose le transmet aux conteneurs :

```yaml
    OPENAI_API_KEY: ${OPENAI_API_KEY:-}
```

Compose remplace `${OPENAI_API_KEY:-}` par la valeur de ton terminal au moment du `docker compose up`. La clé n'est écrite nulle part, et le client `OpenAI()` la trouve tout seul.

@@ hints
- `docker compose config --quiet` ne dit rien si le fichier est valide. S'il cite `redis`, il reste un `depends_on` qui le nomme.
- Dans un conteneur, `localhost` désigne le conteneur lui-même. L'adresse de pgvector, c'est le nom du service : `pgvector`.
- Si `Connection.get("pgvector")` ne trouve rien, vérifie le nom de la variable : `AIRFLOW_CONN_` suivi du nom **en majuscules**. Dans le code, le nom s'écrit en minuscules.
- Si la clé est vide dans le conteneur, tu as lancé `docker compose up` depuis un terminal sans le secret. Ajoute le secret au Codespace, recharge-le, puis `docker compose up -d` à nouveau.
- Après un changement du `Dockerfile` ou du `requirements.txt`, il faut `docker compose build` puis `docker compose up -d` : sinon l'ancienne image continue de tourner.

@@ solution
Les lignes ajoutées ou changées dans `x-airflow-common` :

~~~yaml
x-airflow-common:
  &airflow-common
  build: .                          # l'image du Dockerfile, à la place de image: apache/airflow:3.3.2
  environment:
    &airflow-common-env
    AIRFLOW__CORE__EXECUTOR: LocalExecutor
    AIRFLOW__CORE__LOAD_EXAMPLES: 'false'
    # ... les autres lignes du compose officiel, sans les deux AIRFLOW__CELERY__ ...
    AIRFLOW_CONN_PGVECTOR: postgresql://user:pswd@pgvector:5432/faq
    OPENAI_API_KEY: ${OPENAI_API_KEY:-}
  volumes:
    - ${AIRFLOW_PROJ_DIR:-.}/dags:/opt/airflow/dags
    - ${AIRFLOW_PROJ_DIR:-.}/logs:/opt/airflow/logs
    - ${AIRFLOW_PROJ_DIR:-.}/config:/opt/airflow/config
    - ${AIRFLOW_PROJ_DIR:-.}/plugins:/opt/airflow/plugins
    - ${AIRFLOW_PROJ_DIR:-.}/models:/opt/airflow/models
    - ${AIRFLOW_PROJ_DIR:-.}/data:/opt/airflow/data
  user: "${AIRFLOW_UID:-50000}:0"
  depends_on:
    &airflow-common-depends-on
    postgres:
      condition: service_healthy
    pgvector:
      condition: service_healthy
~~~

~~~python
from datetime import datetime

from airflow.sdk import Connection, dag, task


@dag(schedule=None, start_date=datetime(2026, 11, 1), catchup=False)
def setup_check():

    @task
    def check():
        import os
        import psycopg
        from embedder import Embedder

        with psycopg.connect(Connection.get("pgvector").get_uri()) as conn:
            conn.execute("CREATE EXTENSION IF NOT EXISTS vector")
            print("pgvector", conn.execute("SELECT extversion FROM pg_extension WHERE extname = 'vector'").fetchone()[0])
        v = Embedder("/opt/airflow/models/Xenova/all-MiniLM-L6-v2").encode("Can I still join the course?")
        print("embedding", v.shape)
        key = os.environ.get("OPENAI_API_KEY", "")
        assert key, "OPENAI_API_KEY est vide dans le conteneur"
        print("clé OpenAI", key[:3] + "...")

    check()


setup_check()
~~~
