# Un assistant IA qui connaît ton projet

Écrire un DAG à la main prend du temps : chercher le bon opérateur, le nom exact d'un paramètre, l'ordre des tâches. Dans le cours officiel, Kestra a un **AI Copilot** intégré à son éditeur : tu décris ce que tu veux, il écrit le flow, et il le fait bien parce qu'il connaît la documentation **de ta version** de Kestra.

L'Airflow open source que tu as installé n'a pas d'assistant intégré à son interface. On construit l'équivalent avec ce que tu as déjà : l'assistant de ton éditeur, plus le contexte de la leçon 2, plus une boucle de vérification rapide.

## 🔑 Les trois pièces d'un assistant fiable

| Pièce | Chez Kestra | Chez toi, avec Airflow |
| --- | --- | --- |
| Un assistant | L'AI Copilot dans l'éditeur de flows | GitHub Copilot dans VS Code ou ton Codespace (gratuit avec le pack étudiant de GitHub), ou un autre assistant de code |
| Le contexte | La documentation des plugins de ta version, fournie par Kestra | Ton `CONTEXT.md` de la leçon 2, dans un fichier que l'assistant lit **tout seul** |
| La vérification | Kestra valide le YAML | `airflow dags list-import-errors` et `airflow dags test`, après chaque modification |

Le fichier que l'assistant lit tout seul dépend de l'outil : `.github/copilot-instructions.md` pour GitHub Copilot, `CLAUDE.md` pour Claude Code, `AGENTS.md` pour plusieurs autres. Le contenu est le même : la version, les imports, ce qui est interdit, tes connexions, tes conventions.

## La règle des 5 %

L'assistant fait vite le gros du travail : la structure du DAG, les imports, l'enchaînement des tâches. Il ne connaît pas ton environnement : le nom de ta connexion, ta table, le seuil qui dit qu'une ingestion s'est mal passée, le nombre de relances qui convient à ton service. Ces **5 %** restent à toi. Relis-les toujours : c'est là que se cachent les erreurs qui ne plantent pas.

## Avancer par petites demandes

La conversation est cumulative : chaque demande modifie le DAG existant au lieu de tout réécrire. Le cours officiel propose cette progression, que tu vas refaire avec Airflow :

1. « Crée un DAG qui télécharge la FAQ et la charge dans pgvector. »
2. « Ajoute une tâche qui vérifie la qualité des données chargées. »
3. « Planifie-le tous les jours à 9 h UTC. »
4. « Préviens-moi s'il échoue. »

Après **chaque** étape : `list-import-errors`, puis `dags test`. Une erreur trouvée tout de suite se corrige en une ligne ; quatre erreurs empilées prennent une heure.

@@ brief
- Kestra a un AI Copilot intégré, fiable parce qu'il connaît la documentation de ta version. L'Airflow open source n'en a pas : on assemble l'équivalent.
- 🔑 Trois pièces : un **assistant** dans ton éditeur, un **fichier de contexte** qu'il lit tout seul (`.github/copilot-instructions.md`, `CLAUDE.md` ou `AGENTS.md`), et une **vérification** après chaque modification (`list-import-errors`, `dags test`).
- La règle des **5 %** : l'assistant écrit la structure, toi tu règles ce qu'il ne peut pas savoir (connexion, table, seuils, relances).
- On avance par **petites demandes**, et on vérifie après chacune.

@@ declic
- [03-02] Ton `CONTEXT.md` de la leçon 2 devient le fichier d'instructions de ton assistant : tu ne le colles plus à la main, il est lu à chaque demande.
- [DE:02-07] Dans ton pipeline des taxis, un run vert voulait dire « aucune tâche n'a planté », pas « les données sont justes ». La demande numéro 2 ajoute la tâche qui vérifie la seconde chose.

@@ practice
Fais écrire le DAG `faq_daily` par ton assistant, en quatre demandes, avec ton fichier de contexte. Puis fais les 5 % toi-même, en les marquant dans le code.

@@ constraints
- Ton `CONTEXT.md` de la leçon 2, copié dans le fichier d'instructions de ton assistant
- Le DAG `faq_daily` obtenu par les quatre demandes de la leçon, une par une, avec `list-import-errors` et `dags test` après chacune
- Le contrôle qualité vérifie au moins le nombre de documents, l'absence d'embedding vide et le nombre de cours
- Un commentaire `# 5 %` sur chaque ligne que tu as réglée toi-même
- Un essai où le contrôle qualité **échoue** (un seuil trop haut), pour voir l'alerte se déclencher

@@ guide
### 1. Le fichier de contexte

Pour GitHub Copilot : `mkdir -p .github` à la racine de ton fork, puis copie ton `CONTEXT.md` dans `.github/copilot-instructions.md`. Ajoute une ligne qui dit où sont les DAG : `mon-travail/module-03/airflow/dags/`.

### 2. Les quatre demandes

Dans le chat de ton assistant, en mode qui modifie les fichiers, une demande à la fois. Après chacune :

~~~bash
cd /workspaces/llm-zoomcamp/mon-travail/module-03/airflow
docker compose exec airflow-scheduler airflow dags list-import-errors
docker compose exec airflow-scheduler airflow dags test faq_daily
~~~

### 3. Le contrôle qualité

Une requête SQL suffit : `count(*)`, `count(*) FILTER (WHERE embedding IS NULL)` et `count(DISTINCT course)`. Si une valeur est mauvaise, la tâche lève une exception : le DAG passe au rouge.

### 4. L'alerte

Dans Airflow, « préviens-moi » se traduit par `on_failure_callback` : une fonction appelée avec le contexte de la tâche qui a échoué. Ici, elle affiche un message dans les logs. En entreprise, elle enverrait un message Slack ou un e-mail.

### 5. Les 5 %

Relis chaque ligne : la connexion, la table, le seuil de documents, le nombre de relances, l'heure. Ce que l'assistant a deviné, vérifie-le ou corrige-le, puis marque-le `# 5 %`.

@@ hints
- Si l'assistant écrit encore `schedule_interval` ou `days_ago`, ton fichier d'instructions n'est pas lu : vérifie son nom et son emplacement.
- Un contrôle qualité ne doit pas être relancé : une donnée fausse ne se répare pas en réessayant. Mets `retries=0` sur cette tâche, même si le DAG en a 3 par défaut.
- « Tous les jours à 9 h UTC » s'écrit `schedule="0 9 * * *"`. `"@daily"`, c'est minuit.
- Pour l'essai qui échoue, monte le seuil de documents à 5000, lance `dags test`, puis remets-le.

@@ solution
Mon DAG final, testé dans Airflow 3.3.2 avec ma copie de la FAQ (1470 entrées). Les lignes marquées `# 5 %` sont celles qu'un assistant ne peut pas deviner.

~~~python
"""L'ingestion quotidienne de la FAQ, écrite avec un assistant puis relue : les 5 % sont commentés."""
import json
import os
from datetime import datetime, timedelta
from pathlib import Path

from airflow.sdk import Connection, dag, task

DATA_DIR = Path(os.environ.get("FAQ_DATA_DIR", "/opt/airflow/data"))
MODEL_DIR = os.environ.get("EMBED_MODEL_DIR", "/opt/airflow/models/Xenova/all-MiniLM-L6-v2")
MIN_DOCUMENTS = 1000  # 5 % : un seuil qui vient de notre FAQ (environ 1 500 entrées), pas de l'assistant


def alert(context):
    ti = context["ti"]
    print(f"ALERTE : {ti.dag_id}.{ti.task_id} a échoué (essai {ti.try_number}) pour le run {context['run_id']}")


@dag(
    schedule="0 9 * * *",                      # 5 % : tous les jours à 9 h UTC
    start_date=datetime(2026, 11, 1),
    catchup=False,
    max_active_runs=1,
    default_args={"retries": 3, "retry_delay": timedelta(minutes=1),   # 5 % : notre tolérance aux pannes
                  "retry_exponential_backoff": True, "on_failure_callback": alert},
    tags=["llm-zoomcamp"],
)
def faq_daily():

    @task
    def extract(ds=None):
        from ingest import load_faq_data
        DATA_DIR.mkdir(parents=True, exist_ok=True)
        path = DATA_DIR / f"faq_{ds}.json"
        path.write_text(json.dumps(load_faq_data()))
        return str(path)

    @task
    def load(path):
        import psycopg
        from embedder import Embedder
        docs = json.loads(Path(path).read_text())
        embed = Embedder(MODEL_DIR)
        embed.tokenizer.enable_truncation(256)
        vectors = []
        for i in range(0, len(docs), 50):
            vectors.extend(embed.encode_batch([d["question"] + " " + d["answer"] for d in docs[i:i + 50]]))
        rows = [(d["id"], d["course"], d["section"], d["question"], d["answer"],
                 "[" + ",".join(str(float(x)) for x in v) + "]") for d, v in zip(docs, vectors)]
        with psycopg.connect(Connection.get("pgvector").get_uri()) as conn:   # 5 % : notre connexion
            conn.execute("CREATE EXTENSION IF NOT EXISTS vector")
            conn.execute("""CREATE TABLE IF NOT EXISTS documents (id TEXT PRIMARY KEY, course TEXT, section TEXT,
                            question TEXT, answer TEXT, embedding vector(384))""")
            with conn.cursor() as cur:
                cur.executemany("""
                    INSERT INTO documents (id, course, section, question, answer, embedding)
                    VALUES (%s, %s, %s, %s, %s, %s::vector)
                    ON CONFLICT (id) DO UPDATE SET course = EXCLUDED.course, section = EXCLUDED.section,
                        question = EXCLUDED.question, answer = EXCLUDED.answer, embedding = EXCLUDED.embedding
                """, rows)
        return len(rows)

    @task(retries=0)   # une donnée fausse ne se répare pas en réessayant
    def quality_check(loaded):
        import psycopg
        with psycopg.connect(Connection.get("pgvector").get_uri()) as conn:
            total, missing, courses = conn.execute(
                "SELECT count(*), count(*) FILTER (WHERE embedding IS NULL), count(DISTINCT course) FROM documents").fetchone()
        print(f"{loaded} chargés, {total} en tout, {missing} sans embedding, {courses} cours")
        if total < MIN_DOCUMENTS or missing or courses < 2:
            raise ValueError(f"Contrôle qualité raté : {total} documents, {missing} sans embedding, {courses} cours")

    quality_check(load(extract()))


faq_daily()
~~~

Ce que j'obtiens : `1470 chargés, 1470 en tout, 0 sans embedding, 6 cours`. Avec `MIN_DOCUMENTS = 5000`, la tâche `quality_check` échoue et les logs affichent `ALERTE : faq_daily.quality_check a échoué (essai 1)`. Je n'ai pas pu tester d'assistant de code depuis mon environnement : ton DAG peut être écrit autrement, du moment qu'il passe les mêmes vérifications.

@@ selfcheck

- `faq_daily` passe au vert, et au rouge avec un seuil trop haut, avec le message d'alerte dans les logs
- Chaque ligne réglée par toi porte un commentaire `# 5 %`
- `quality_check` ne se relance pas quand il échoue

@@ explain
Qu'est-ce qui rend un assistant IA fiable pour écrire des DAG ? Et quels 5 % ne doit-on jamais lui laisser sans les relire ?

@@ cles
- Les instructions d'un assistant de code | github copilot custom instructions repository | Donner son contexte à l'assistant une fois pour toutes.
- Les callbacks d'Airflow | airflow on_failure_callback | Réagir à un échec : alerter, nettoyer, enregistrer.
- Les contrôles qualité de données | data quality checks pipeline | Arrêter un pipeline avant qu'une donnée fausse n'atteigne les utilisateurs.
