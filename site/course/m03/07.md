# Plusieurs agents qui collaborent

Pour une tâche complexe, on peut répartir le travail entre plusieurs agents spécialisés. Le cours officiel le fait avec deux agents : un **chercheur**, qui a l'outil de recherche, et un **analyste**, qui ne cherche rien lui-même mais utilise le chercheur **comme un outil**. L'analyste pose ses questions au chercheur exactement comme il appellerait une fonction, puis rédige un rapport en JSON.

Les avantages : chaque agent a un seul rôle et des instructions courtes, et quand quelque chose rate, on sait lequel regarder.

## Deux architectures

Avec Airflow, tu as deux façons de faire travailler plusieurs agents, et la différence compte.

**1. L'agent-outil, comme dans le cours officiel.** Une seule tâche Airflow. L'analyste a un outil `ask_researcher(question)`, qui lance un `Agent` chercheur et renvoie sa réponse. C'est l'analyste qui décide combien de questions poser, et lesquelles.

**2. Les chercheurs en parallèle, lancés par Airflow.** Une tâche `research` par question, créées au moment du run avec le **dynamic task mapping** : `research.expand(question=questions())`. Airflow les lance en parallèle, réessaie chacune séparément, et montre chacune dans l'interface. Une dernière tâche, `synthesis`, reçoit toutes les réponses et rédige le rapport.

| | L'agent-outil | Les chercheurs en parallèle |
| --- | --- | --- |
| Qui choisit les questions | Le modèle | Toi, ou une tâche avant |
| Tâches Airflow | Une seule | Une par question, plus la synthèse |
| Si un appel échoue | Toute la tâche recommence | Seule cette question recommence |
| Ce que montre l'interface | Une tâche, des logs | Chaque recherche, sa durée, son résultat |
| Quand l'utiliser | On ne sait pas à l'avance quoi chercher | On connaît la liste des questions |

## 🔑 Limiter les appels simultanés

Dix chercheurs en parallèle, c'est dix appels à l'API en même temps, et vite une erreur `429`. Airflow a un outil pour ça : un **pool**, un nombre de places partagées. `airflow pools set openai 2 "Appels OpenAI"` crée un pool de deux places ; `@task(pool="openai")` fait attendre une tâche qu'une place se libère. Le pool est partagé par **tous** les DAG : c'est la bonne façon de respecter une limite de débit de ton compte, pas seulement d'un DAG.

## 🔑 Le JSON d'un modèle se vérifie

L'analyste doit répondre en JSON. Le prompt du cours officiel insiste : « pas de markdown, jamais de ```json ». Malgré ça, un modèle ajoute parfois ces balises, et `json.loads` échoue. La tâche qui lit le rapport doit donc nettoyer avant de lire, ou mieux, demander à l'API une **sortie structurée**, qui garantit un JSON conforme à un schéma.

@@ predict
Dans l'architecture agent-outil, ta tâche affiche les tokens renvoyés par `Agent.run` de l'analyste. Est-ce le coût du run ? Sinon, quelle part du vrai coût montre-t-il, à peu près ?

@@ predict-answer
**Non.** `Agent.run` additionne les tokens des appels **de l'analyste**. Les appels du chercheur se font dans l'outil `ask_researcher`, avec leur propre `Agent.run` : leurs tokens ne remontent nulle part, sauf si tu les comptes toi-même.

Dans mon essai, l'analyste affichait 350 tokens, et ses chercheurs en avaient consommé 1 450 de plus : le compteur de l'analyste montrait moins de **20 %** du coût réel. Le chercheur reçoit les cinq documents de la FAQ à chaque recherche ; l'analyste ne reçoit que sa réponse courte. Dans un système à plusieurs agents, le coût est là où les documents sont lus, souvent dans les agents qu'on ne voit pas.

@@ guide
### 1. Le module partagé

Déplace `search_faq` et les instructions de la leçon 6 dans `dags/faq_tools.py`, et importe-les : `from faq_tools import search_faq, INSTRUCTIONS`. Un fichier sans DAG peut être importé par tous les autres (l'erreur provoquée de cette leçon montre pourquoi c'est nécessaire).

### 2. L'agent-outil et son compteur

Dans la tâche `analysis`, un dictionnaire `spent = {"input_tokens": 0, "output_tokens": 0}`, puis une fonction **locale** `ask_researcher(question: str) -> str` avec une docstring : elle lance un `Agent` chercheur, ajoute ses tokens à `spent`, et renvoie sa réponse. Une fonction définie dans la tâche voit les variables de la tâche.

### 3. Les chercheurs en parallèle

Une tâche `questions` qui renvoie `params["questions"]`, puis `research.expand(question=questions())`. Chaque instance reçoit **une** question. `synthesis(findings)` reçoit la liste de leurs résultats : `list(findings)` pour la parcourir.

### 4. Le pool

Une fois : `docker compose exec airflow-scheduler airflow pools set openai 2 "Appels OpenAI simultanés"`. Puis `@task(pool="openai")` sur `research`. Un pool qui n'existe pas laisse la tâche en attente, sans erreur claire.

### 5. Lire le JSON

Une fonction `parse_json(text)` : si le texte commence par ```, retire la première et la dernière ligne, puis `json.loads`.

@@ solution
`dags/faq_tools.py` contient `search_faq` et les instructions de la leçon 6, sans DAG. Puis `dags/faq_team.py` :

~~~python
"""Deux façons de faire travailler plusieurs agents : un analyste qui appelle un chercheur comme un outil,
et des chercheurs lancés en parallèle par Airflow, puis un analyste qui fait la synthèse."""
import json
from datetime import datetime, timedelta

from airflow.sdk import Param, dag, task

from faq_tools import INSTRUCTIONS as RESEARCH_INSTRUCTIONS, search_faq

LLM_ARGS = {"retries": 2, "retry_delay": timedelta(seconds=20), "retry_exponential_backoff": True,
            "execution_timeout": timedelta(minutes=10)}

ANALYST_INSTRUCTIONS = """You're a senior course advisor. A student is about to start the LLM Zoomcamp.
Use the ask_researcher tool for each thing you need to know. Then answer with a valid JSON object only, no markdown:
{"summary": "...", "answers": [{"topic": "...", "finding": "..."}], "gaps": ["what the FAQ doesn't say"]}"""

SYNTHESIS_INSTRUCTIONS = """You're a senior course advisor. Write a JSON object only, no markdown, from the findings:
{"summary": "...", "answers": [{"topic": "...", "finding": "..."}], "gaps": ["what the FAQ doesn't say"]}"""


def parse_json(text):
    text = text.strip()
    if text.startswith("```"):
        text = text.split("\n", 1)[1].rsplit("```", 1)[0]
    return json.loads(text)


@dag(schedule=None, start_date=datetime(2026, 11, 1), catchup=False, default_args=LLM_ARGS,
     params={"student_profile": Param("I work full time, I know Python, I have no GPU and I join two weeks late.", type="string")},
     tags=["llm-zoomcamp", "agents"])
def faq_team_tool():

    @task
    def analysis(params=None):
        from openai import OpenAI
        from agentkit import Agent
        client = OpenAI()
        spent = {"input_tokens": 0, "output_tokens": 0}

        def ask_researcher(question: str) -> str:
            """Ask the research assistant one precise question about the course. It searches the FAQ.

            Args:
                question: One precise question, in English.
            """
            r = Agent(client, RESEARCH_INSTRUCTIONS, tools=[search_faq]).run(question)
            spent["input_tokens"] += r["input_tokens"]
            spent["output_tokens"] += r["output_tokens"]
            return r["answer"]

        result = Agent(client, ANALYST_INSTRUCTIONS, tools=[ask_researcher], max_iterations=6).run(params["student_profile"])
        print(f"analyste : {result['input_tokens']} + {result['output_tokens']} tokens ; "
              f"chercheurs : {spent['input_tokens']} + {spent['output_tokens']} tokens")
        return {"report": parse_json(result["answer"]),
                "tokens": result["input_tokens"] + result["output_tokens"] + spent["input_tokens"] + spent["output_tokens"]}

    analysis()


faq_team_tool()


@dag(schedule=None, start_date=datetime(2026, 11, 1), catchup=False, default_args=LLM_ARGS,
     params={"questions": Param(["Can I join the course late?", "Do I need a GPU?", "Is there a certificate?"],
                                type="array", minItems=1, maxItems=10)},
     tags=["llm-zoomcamp", "agents"])
def faq_team_mapped():

    @task
    def questions(params=None):
        return params["questions"]

    @task(pool="openai", max_active_tis_per_dag=2)
    def research(question):
        from openai import OpenAI
        from agentkit import Agent
        r = Agent(OpenAI(), RESEARCH_INSTRUCTIONS, tools=[search_faq]).run(question)
        return {"question": question, "finding": r["answer"], "tokens": r["input_tokens"] + r["output_tokens"]}

    @task
    def synthesis(findings):
        from openai import OpenAI
        findings = list(findings)
        response = OpenAI().responses.create(
            model="gpt-5.4-mini",
            input=[{"role": "developer", "content": SYNTHESIS_INSTRUCTIONS},
                   {"role": "user", "content": json.dumps(findings)}])
        tokens = sum(f["tokens"] for f in findings) + response.usage.input_tokens + response.usage.output_tokens
        print(f"{len(findings)} recherches, {tokens} tokens en tout")
        return {"report": parse_json(response.output_text), "tokens": tokens}

    synthesis(research.expand(question=questions()))


faq_team_mapped()
~~~

Testé dans Airflow 3.3.2 avec un faux client, sans erreur d'import : l'agent-outil affiche `analyste : 310 + 40 tokens ; chercheurs : 1410 + 40 tokens`, la version parallèle `3 recherches, 2408 tokens en tout`. Ces nombres viennent du faux client : les tiens seront ceux du vrai modèle, et c'est ton tableau qui dira laquelle des deux coûte le moins sur ta mission.

@@ breakfix-answer
Airflow signale une erreur sur `faq_team.py` :

~~~text
AirflowDagDuplicatedIdException: Ignoring DAG faq_agent from .../faq_team.py - also found in .../faq_agent.py
~~~

Importer un module, c'est **exécuter** le fichier. La dernière ligne de `faq_agent.py` appelle `faq_agent()`, qui déclare le DAG : en important l'outil, `faq_team.py` déclare **aussi** le DAG `faq_agent`. Airflow trouve le même identifiant dans deux fichiers, et marque le second en erreur.

La règle : un fichier de DAG ne s'importe jamais. Le code partagé va dans un module sans DAG (`faq_tools.py`), importé par tous. C'est aussi plus clair : un fichier, un rôle.
