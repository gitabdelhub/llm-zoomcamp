# Coûts, secrets et limites

La leçon officielle « Best Practices » fait le tour de ce qui sépare une démo d'un pipeline qu'on laisse tourner seul : les coûts, les secrets, les logs, et ce qu'il faut faire avant la production. Elle le montre avec Kestra et Gemini. Les principes sont les mêmes avec Airflow et OpenAI, et deux d'entre eux méritent qu'on s'y arrête, parce qu'ils coûtent cher quand on les rate : **relancer la bonne erreur** et **ne jamais afficher une clé**.

## Quel outil pour quel travail

Le tableau du cours officiel, traduit pour ton installation :

| Situation | Ce qu'on utilise | Pourquoi |
| --- | --- | --- |
| Écrire ou modifier un DAG | Ton assistant de code, avec ton contexte (leçon 4) | C'est le plus rapide, et `dags test` vérifie |
| Répondre à partir de tes données | Le RAG (leçon 5) | La réponse s'appuie sur des documents réels |
| Un pipeline fixe, qui se répète | Un DAG classique, sans modèle | Déterministe, prévisible, auditable |
| Une recherche dont on ne connaît pas les étapes | Un agent (leçon 6) | Il s'adapte à ce qu'il trouve |
| Un objectif complexe, en plusieurs parties | Plusieurs agents (leçon 7) | Chaque agent a un seul rôle |

## Les coûts

Le cours officiel donne les prix de Gemini ; tu utilises OpenAI. Dans les deux cas, les prix changent : garde-les dans deux constantes, comme au module 1, et relis la page des prix le jour où tu calcules.

Les leviers du cours officiel, dans Airflow :

1. **Un petit modèle** pour les tâches simples. `gpt-5.4-mini` suffit à un résumé ou à un RAG sur la FAQ.
2. **Un plafond de réponse** : `max_output_tokens` dans chaque appel. Sans lui, un modèle qui s'emballe peut écrire des milliers de tokens.
3. **Compter les tokens à chaque run** : tes DAG les affichent déjà (leçons 5 à 7). Un DAG planifié `@daily` qui coûte 0,01 $ par run coûte 3,65 $ par an ; le même, lancé par 50 tâches mappées, cinquante fois plus.
4. **Pas de modèle quand une règle suffit.** Un filtre, une jointure, un seuil : du Python ou du SQL, gratuits et toujours identiques.

## 🔑 Relancer seulement ce qui peut réussir plus tard

Tes DAG d'IA ont `retries=2` ou `3`. C'est bien pour une erreur **passagère** : l'API est surchargée, le réseau a coupé. C'est du temps et de l'argent perdus pour une erreur **définitive** : une clé fausse ne deviendra pas juste en attendant cinq minutes.

| Erreur de l'API | Code | Relancer ? |
| --- | --- | --- |
| `RateLimitError`, trop de requêtes | 429 | Oui, plus tard |
| `RateLimitError`, `insufficient_quota` | 429 | **Non** : le compte est vide, il faut payer |
| `InternalServerError` | 500, 503 | Oui |
| `APIConnectionError`, `APITimeoutError` | aucun | Oui |
| `AuthenticationError` | 401 | Non : la clé est fausse |
| `BadRequestError` | 400 | Non : la requête est mal faite (trop longue, paramètre inconnu) |

Deux pièges dans ce tableau. Le quota épuisé arrive avec le **même** code 429 qu'une surcharge : seul `error.code` les distingue. Et le client OpenAI **relance déjà tout seul** : deux fois par défaut (`max_retries=2`), après quelques secondes, pour les erreurs passagères. Les retries d'Airflow viennent après, avec des minutes d'écart. Deux étages, deux rythmes.

Pour faire échouer une tâche **sans** ses retries, Airflow a une exception : `AirflowFailException`, dans `airflow.sdk.exceptions`.

## 🔑 Les secrets n'apparaissent jamais dans un log

Ta clé vient d'un secret de Codespaces, `OPENAI_API_KEY`, que le `docker-compose.yaml` passe aux conteneurs. Elle n'est jamais dans un fichier du dépôt. Reste un endroit où elle fuit sans que tu le voies : **les logs**.

Airflow masque (`***`) dans les logs des tâches les valeurs des connexions, et celles des variables dont le **nom** contient un mot sensible : `api_key`, `password`, `secret`, `token`… Il ne masque rien d'autre. Une variable d'environnement, il ne la connaît pas : il faut la lui déclarer avec `mask_secret(valeur)`, de `airflow.sdk.log`. Et **`airflow dags test` ne masque rien du tout** : ce que tu affiches en le testant apparaît en clair dans ton terminal.

La règle tient en une ligne : on n'affiche jamais une clé, même pour déboguer. Pour vérifier qu'elle est là, affiche sa **présence** : `print("clé présente :", bool(os.environ.get("OPENAI_API_KEY")))`.

Si une clé a été poussée sur GitHub : **révoque-la tout de suite** sur la page des clés d'OpenAI, puis crée-en une autre. Réécrire l'historique Git ne suffit pas : des robots lisent les dépôts publics en quelques minutes.

## Avant la production

La liste du cours officiel, avec les outils d'Airflow :

1. **Tester plusieurs fois**, avec des entrées différentes : un modèle ne répond pas deux fois pareil. `faq_check` (leçon 5) le fait après chaque mise à jour.
2. **Prévoir l'échec** : des retries pour les erreurs passagères, un `on_failure_callback` pour être prévenu (leçon 4).
3. **Poser des limites** : `max_output_tokens` par appel, `max_iterations` par agent, `execution_timeout` par tâche, un pool pour tous les DAG.
4. **Documenter** : une docstring par DAG, qui dit ce que fait l'agent et ce qu'il a le droit de faire.

@@ guide
### 1. Trier les erreurs

Toutes les erreurs de l'API héritent de `openai.APIError`. Un tuple `TRANSIENT` avec les trois classes passagères, et `isinstance(exc, TRANSIENT)` fait le tri. Ajoute d'abord le cas particulier : une `RateLimitError` dont `exc.code == "insufficient_quota"` n'est pas passagère.

### 2. Un seul point de passage

`run_guarded` appelle `fn` dans un `try`. Dans le `except openai.APIError as e` : si l'erreur est passagère, `raise` tout court la relance telle quelle ; sinon, `raise AirflowFailException(...) from e`. Le `from e` garde l'erreur d'origine dans le log.

### 3. Tester sans réseau

Une erreur de l'API se fabrique : `openai.RateLimitError("boom", response=httpx.Response(429, request=req), body={"code": "rate_limit_exceeded"})`, avec `req = httpx.Request("POST", "https://api.openai.com/v1/responses")`. `APIConnectionError` ne prend que `request=req`. Un faux client dont `responses.create` lève cette erreur, et tu vérifies ce que `call_llm` laisse sortir.

Le script a besoin d'Airflow : lance-le dans le conteneur, en lui donnant le fichier sur l'entrée standard, comme le vérificateur du défi.

~~~bash
docker compose exec -T airflow-scheduler python - < tests/test_llm_guard.py
~~~

### 4. Brancher les DAG

Dans `ask_llm`, remplace `OpenAI().responses.create(...)` par `call_llm(OpenAI(), ...)`. Dans la tâche `agent`, remplace `bot.run(question)` par `run_guarded(bot.run, question)`. Relance `list-import-errors`, puis `dags test`.

### 5. Le coût par mois

Les tokens d'un run de chaque DAG qui appelle le modèle, multipliés par tes deux prix, puis par 10 runs et par 30 jours. Tes DAG planifiés, `faq_ingest` et `faq_daily`, n'appellent jamais le modèle : les embeddings sont calculés dans ton conteneur, gratuitement. Écris-le aussi, c'est un résultat : le coût d'un projet d'IA n'est pas forcément là où tourne le planning.

@@ hints
- Le script de test fait `sys.path.insert(0, "/opt/airflow/dags")` avant `from llm_guard import call_llm` : sans ça, Python ne trouve pas ton module.
- Garde le dossier `tests/` **hors** de `dags/` : Airflow ne doit pas lire tes tests comme des DAG.

@@ solution
`dags/llm_guard.py` :

~~~python
"""Les appels au modèle, protégés : on ne relance que ce qui peut réussir plus tard.
Ce fichier ne contient aucun DAG : tous les DAG d'IA peuvent l'importer."""
import openai
from airflow.sdk.exceptions import AirflowFailException

# Les erreurs passagères : réessayer plus tard peut réussir.
TRANSIENT = (openai.RateLimitError, openai.APIConnectionError, openai.InternalServerError)


def is_transient(exc):
    if isinstance(exc, openai.RateLimitError) and exc.code == "insufficient_quota":
        return False  # aussi un 429, mais attendre ne remplira pas le compte
    return isinstance(exc, TRANSIENT)


def run_guarded(fn, *args, **kwargs):
    """Appelle fn. Une erreur définitive de l'API fait échouer la tâche tout de suite, sans retries."""
    try:
        return fn(*args, **kwargs)
    except openai.APIError as e:
        if is_transient(e):
            raise  # Airflow relancera la tâche plus tard
        raise AirflowFailException(f"{type(e).__name__} : relancer ne changera rien. {e}") from e


def call_llm(client, **kwargs):
    kwargs.setdefault("max_output_tokens", 1000)
    return run_guarded(client.responses.create, **kwargs)
~~~

`tests/test_llm_guard.py` :

~~~python
"""Vérifie le tri des erreurs sans aucun appel à l'API.
docker compose exec -T airflow-scheduler python - < tests/test_llm_guard.py"""
import sys

sys.path.insert(0, "/opt/airflow/dags")

import httpx
import openai
from airflow.sdk.exceptions import AirflowFailException

from llm_guard import call_llm

REQUEST = httpx.Request("POST", "https://api.openai.com/v1/responses")


def status_error(cls, status, code=None):
    return cls("boom", response=httpx.Response(status, request=REQUEST), body={"code": code} if code else None)


CASES = [
    ("trop de requêtes", status_error(openai.RateLimitError, 429, "rate_limit_exceeded"), True),
    ("quota épuisé", status_error(openai.RateLimitError, 429, "insufficient_quota"), False),
    ("panne du serveur", status_error(openai.InternalServerError, 503), True),
    ("réseau coupé", openai.APIConnectionError(request=REQUEST), True),
    ("délai dépassé", openai.APITimeoutError(request=REQUEST), True),
    ("mauvaise clé", status_error(openai.AuthenticationError, 401, "invalid_api_key"), False),
    ("requête invalide", status_error(openai.BadRequestError, 400), False),
]


class Failing:
    """Un faux client dont l'appel lève toujours la même erreur."""
    def __init__(self, error):
        self.responses = self
        self.error = error

    def create(self, **kwargs):
        raise self.error


for name, error, transient in CASES:
    try:
        call_llm(Failing(error), model="gpt-5.4-mini", input="test")
    except AirflowFailException:
        relaunched = False
    except openai.APIError:
        relaunched = True
    assert relaunched == transient, f"{name} : relancée={relaunched}, attendu {transient}"
    print(f"ok  {name:18} {'relancée' if transient else 'échec définitif'}")
print("Les 7 erreurs sont bien triées.")
~~~

@@ cles
- Les erreurs passagères et définitives | transient vs permanent errors retry | Ne relancer que ce qui peut réussir plus tard.
- Le backoff exponentiel | exponential backoff jitter rate limit | Espacer de plus en plus les relances, pour ne pas surcharger l'API.
- Le masquage des secrets dans Airflow | airflow secrets masker mask_secret | Ce qu'Airflow cache dans les logs, et ce qu'il ne voit pas.
- Les fuites de secrets sur GitHub | github secret scanning leaked api key | Pourquoi une clé poussée doit être révoquée, pas seulement effacée.
