# Bilan : quand un agent, quand un DAG

Dans ce module, tu as fait avec Airflow 3 tout ce que le cours officiel fait avec Kestra : un contexte qui empêche ton assistant d'écrire du vieil Airflow, un assistant de code qui connaît ton projet, un RAG dont l'ingestion tourne chaque jour, un agent dans une tâche, plusieurs agents qui collaborent, et les protections qui permettent de laisser tout ça tourner seul.

## La question à se poser avant chaque tâche

**Est-ce que je connais les étapes à l'avance ?**

- **Oui** : c'est un DAG classique. Télécharger, transformer, charger, vérifier. Chaque run fait la même chose, coûte la même chose, et se rejoue à l'identique. C'est le cas de `faq_ingest` et de `faq_daily` : aucun modèle de langage, et c'est très bien.
- **Oui, mais une étape demande de comprendre un texte** : un DAG classique, avec **un** appel au modèle à cette étape. Résumer, classer, extraire un champ. Le DAG garde la main sur l'ordre ; le modèle ne fait que ce qu'on lui demande. C'est `faq_ask` et `simple_agent`.
- **Non, les étapes dépendent de ce qu'on trouve** : un agent, **dans** une tâche, avec un nombre maximal d'itérations, un délai maximal et un budget. C'est `faq_agent`.
- **Non, et le travail se découpe en parties indépendantes** : plusieurs agents, et si tu connais les parties, laisse Airflow les lancer en parallèle (`faq_team_mapped`) plutôt qu'un agent qui décide de tout.

Dans tous les cas, l'orchestrateur reste au-dessus : c'est lui qui planifie, relance, limite et garde les traces. Un agent ne remplace pas un DAG ; il en devient une tâche.

## Ce qui manque encore

Tu sais maintenant faire tourner un assistant tous les jours. Tu ne sais pas encore s'il répond **bien**. `faq_check` vérifie une seule question ; ton tableau de la leçon 7 compare deux architectures sur une seule mission. Pour décider qu'un changement de prompt, de modèle ou de recherche améliore les réponses, il faut les mesurer sur des centaines de questions : c'est l'objet du module 4.
