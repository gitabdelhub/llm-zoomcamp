@@ brief
- Le module 4 évaluait ton système **avant** que quelqu'un s'en serve, sur un jeu de test fixe. Le module 5 le surveille **pendant** qu'il sert : c'est l'évaluation **en ligne**, qu'on appelle le monitoring.
- Pour chaque question qui arrive, on garde tout ce qui compte : les instructions, le prompt et le modèle, les tokens d'entrée et de sortie, le **coût**, le **temps de réponse**, l'avis de l'utilisateur (👍 ou 👎) et un avis automatique de **pertinence**.
- Trois pièces nouvelles : une **interface** où l'on pose les questions (Streamlit), une **base** qui garde chaque échange (PostgreSQL), et un **tableau de bord** qui les montre (Streamlit, puis Grafana).
- 🔑 On ne réécrit pas le RAG : on l'**enveloppe**. Le même `RAGBase` qu'au module 1, avec une sous-classe qui mesure chaque appel au LLM.
- Le cours suit un RAG. Pour un agent, c'est la même chose avec plus d'étapes : chaque appel d'outil se mesure comme un appel au LLM.

@@ codespaces
- Tout le module se fait dans `mon-travail/module-05/`, un projet uv que tu crées à la leçon 2. Ta clé reste le secret Codespaces `OPENAI_API_KEY` : pas besoin de la recopier dans un fichier.
- Docker tourne dans ton Codespace : Postgres et Grafana y démarrent comme au Zoomcamp DE. Codespaces ouvre lui-même les ports (8501 pour l'application, 3000 pour Grafana).
- Le dossier `05-monitoring/code/` de ton fork contient le code **final** de tout le module. C'est un corrigé : écris le tien leçon par leçon, et ne l'ouvre qu'en cas de blocage.
