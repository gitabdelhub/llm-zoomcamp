@@ brief
- Les mesures disparaissent quand l'application s'arrête : on les range dans **PostgreSQL**, qui ne sert qu'au monitoring. Postgres parce qu'il gère bien les données structurées, et que Grafana s'y branche facilement.
- Postgres tourne dans Docker, sur un **réseau** Docker nommé `monitoring` : Grafana le rejoindra plus tard et trouvera Postgres **par son nom** (`course-assistant-pg`). Un volume nommé (`pgdata`) garde les données entre deux démarrages.
- La table `conversations` reprend les champs de `LLMCallRecord`, plus la **question** de l'utilisateur et le **cours**. 🔑 La date est en `TIMESTAMP WITH TIME ZONE` : sans fuseau horaire, Grafana placerait mal les points sur son axe du temps.
- `db_init.py` crée la table, `db_save.py` insère un enregistrement avec des **paramètres** `%s` et récupère l'`id` grâce à `RETURNING id` : il servira à rattacher l'avis de l'utilisateur à la bonne conversation.
- La question est rangée à part du prompt : le prompt est tout le texte envoyé au modèle (question + contexte), la question est ce que l'utilisateur a vraiment tapé.

@@ predict
Tu as lancé `db_init.py`, puis enregistré trois conversations. Tu relances `db_init.py` pour vérifier que tout va bien. Que se passe-t-il, et que deviennent tes trois conversations ?

@@ predict-answer
Le script plante : `DuplicateTable: relation "conversations" already exists`. Tes trois conversations sont **intactes** : `CREATE TABLE` a échoué avant de toucher à quoi que ce soit, et `conn.commit()` n'a jamais été appelé.

Le vrai problème vient à la leçon 8 : il faudra relancer `db_init.py` pour créer la table `feedback`. Il plantera sur `conversations` **avant** d'arriver à `feedback`. Un script d'initialisation doit pouvoir tourner autant de fois qu'on veut : on dit qu'il est **idempotent**.

@@ practice
Rends l'initialisation **idempotente** : `db_init.py` et `make postgres` doivent pouvoir tourner deux fois de suite sans erreur et sans rien perdre.

@@ constraints
- `db_init.py` lancé deux fois de suite : pas d'erreur, et les conversations déjà enregistrées sont toujours là
- `init_db(drop=True)` recrée toujours une table vide, pour quand tu changes de schéma
- `db_init.py` affiche le nombre de conversations dans la table après l'initialisation
- La cible `network` du `Makefile` ne crée le réseau que s'il n'existe pas
- Vérifie la table avec `\d conversations` dans psql

@@ guide
### 1. CREATE TABLE IF NOT EXISTS

Postgres sait ne créer une table que si elle manque : `CREATE TABLE IF NOT EXISTS conversations (...)`. Si elle existe, il ne fait rien, sans erreur. Attention : il ne vérifie pas que la table existante a les mêmes colonnes.

### 2. Compter

Après le `CREATE`, un `SELECT COUNT(*) FROM conversations` et `cur.fetchone()[0]`.

### 3. Un réseau seulement s'il manque

`docker network inspect monitoring` réussit si le réseau existe, échoue sinon. Avec `||`, la commande de droite ne tourne que si celle de gauche a échoué.

### 4. Regarder la table

~~~bash
docker exec -it course-assistant-pg psql -U user -d course_assistant -c "\d conversations"
~~~

@@ hints
- `>/dev/null 2>&1` cache la sortie et les erreurs de `docker network inspect` : seul son code de retour compte.
- Si `\d conversations` ne montre pas `timestamp with time zone`, relis le type de la colonne `timestamp`.
- Pour tester « sans rien perdre » : enregistre une conversation avec `assistant.py`, relance `db_init.py`, et regarde le compte affiché.

@@ solution
~~~python
def init_db(drop=False):
    conn = get_db_connection()
    try:
        with conn.cursor() as cur:
            if drop:
                cur.execute("DROP TABLE IF EXISTS conversations")
            cur.execute("""
                CREATE TABLE IF NOT EXISTS conversations (
                    id SERIAL PRIMARY KEY,
                    question TEXT NOT NULL,
                    answer TEXT NOT NULL,
                    course TEXT NOT NULL,
                    model TEXT NOT NULL,
                    instructions TEXT NOT NULL,
                    prompt TEXT NOT NULL,
                    prompt_tokens INTEGER NOT NULL,
                    completion_tokens INTEGER NOT NULL,
                    total_tokens INTEGER NOT NULL,
                    response_time FLOAT NOT NULL,
                    cost FLOAT NOT NULL,
                    timestamp TIMESTAMP WITH TIME ZONE NOT NULL
                )
            """)
            cur.execute("SELECT COUNT(*) FROM conversations")
            print(f"conversations: {cur.fetchone()[0]} ligne(s)")
        conn.commit()
    finally:
        conn.close()
~~~

@@ breakfix
Dans `save_conversation`, un collègue « simplifie » la requête avec une f-string : `VALUES ('{question}', ...)` au lieu des `%s`. Ça marche pour « How do I join the course? ». Essaie maintenant avec « What's the deadline for the project? ». Que se passe-t-il, et pourquoi les `%s` ne sont-ils pas un détail ?

@@ breakfix-hints
- Regarde où tombe l'apostrophe de « What's » dans la requête SQL une fois la f-string remplie.
- Qui écrit la question ? Et s'il écrivait autre chose qu'une apostrophe ?

@@ breakfix-answer
Postgres refuse la requête : `psycopg.errors.SyntaxError: syntax error at or near "s"`. L'apostrophe de « What's » **ferme** la chaîne SQL ouverte par `'`, et le reste (`s the deadline...`) devient du SQL.

Une apostrophe casse la requête ; un texte bien choisi pourrait la **modifier** : c'est l'**injection SQL**, et c'est l'utilisateur qui tape la question. Avec `%s`, psycopg envoie la valeur **à part** de la requête : la même question est enregistrée telle quelle, apostrophe comprise. Règle sans exception : jamais de f-string pour mettre une valeur dans du SQL.

@@ explain
Qu'est-ce qu'un script idempotent, et pourquoi un script d'initialisation de base doit-il l'être ?

@@ cles
- L'idempotence | idempotent database migration | Un script qu'on peut relancer sans erreur et sans effet de plus.
- CREATE TABLE IF NOT EXISTS | postgres create table if not exists | Créer une table seulement si elle manque.
- Les requêtes paramétrées | psycopg parameterized queries sql injection | Les valeurs voyagent à part du SQL : ni bug d'apostrophe, ni injection.
- RETURNING | postgres insert returning id | Récupérer l'identifiant créé par l'INSERT, sans seconde requête.
