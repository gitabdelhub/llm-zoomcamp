@@ brief
- Le tableau de bord lira les conversations dans la base : `db_query.py` les récupère, **les plus récentes d'abord** (`ORDER BY timestamp DESC LIMIT 10`).
- Une ligne de Postgres arrive comme un **tuple** : il faudrait se souvenir que la colonne 4 est le modèle et la 6 le prompt. `row_to_record` la retransforme en `LLMCallRecord`, la dataclass de la leçon 4.
- 🔑 La leçon le signale en passant : il n'y a **pas d'index** sur `timestamp`. Pour trouver les 10 plus récentes, Postgres doit alors lire **toute** la table. Avec quelques lignes, aucune différence ; avec des milliers, le tableau de bord ralentit à chaque rafraîchissement.
- Deux solutions : trier par `id` (qui a déjà son index, et croît avec le temps), ou créer un index sur `timestamp`. Les tableaux de bord de Grafana filtrent tous par date : l'index est le bon choix.

@@ verified
Sur une table de **50 000** conversations réparties sur 30 jours, avec `EXPLAIN ANALYZE SELECT * FROM conversations ORDER BY timestamp DESC LIMIT 10` :

- sans index : `Seq Scan on conversations` sur les 50 000 lignes, puis un tri `top-N heapsort` : **7,6 ms** ;
- avec l'index : `Index Scan Backward using conversations_timestamp_idx` : **0,05 ms**, environ 150 fois moins ;
- trier par `id` à la place utilise l'index de la clé primaire (`conversations_pkey`) et va aussi vite.

Tes temps seront un peu différents ; l'ordre de grandeur et le nom des étapes, non.

@@ declic
- [DE:03-02] Dans BigQuery, tu partitionnais les tables par date pour ne pas tout relire. Dans Postgres, l'outil pour ça, c'est l'index.
- [DE:01-10] `ORDER BY ... DESC LIMIT 10`, tu l'as écrit des dizaines de fois sur les taxis. Ici, tu regardes enfin **comment** Postgres l'exécute.

@@ guide
### 1. Une base de test

Dans psql : `CREATE DATABASE test_index;`. Puis lance `db_init.py` avec `POSTGRES_DB=test_index` devant : il crée la table dans cette base.

### 2. 50 000 lignes d'un coup

`generate_series(1, 50000)` fabrique 50 000 lignes ; `now() - random() * interval '30 days'` donne une date au hasard dans le mois.

### 3. Lire un plan

`EXPLAIN ANALYZE` devant la requête l'exécute et montre ce que Postgres a fait. Lis de bas en haut : `Seq Scan` lit toute la table, `Index Scan` passe par un index, `actual time` est le temps réel.

@@ hints
- Toutes les colonnes de `conversations` sont `NOT NULL` : ton `INSERT ... SELECT` doit donner une valeur à chacune.
- Après un gros `INSERT`, `ANALYZE conversations;` met à jour les statistiques que Postgres utilise pour choisir son plan.
- Le nom de l'index : `conversations_timestamp_idx`. Le même nom que dans le défi du module.

@@ solution
~~~sql
-- dans psql, connecté à la base test_index
INSERT INTO conversations (question, answer, course, model, instructions, prompt, prompt_tokens,
    completion_tokens, total_tokens, response_time, cost, timestamp)
SELECT 'q' || g, 'a', 'llm-zoomcamp', 'gpt-5.4-mini', '', 'p', 100, 50, 150, random() * 5, 0.0001,
       now() - random() * interval '30 days'
FROM generate_series(1, 50000) g;
ANALYZE conversations;

EXPLAIN ANALYZE SELECT * FROM conversations ORDER BY timestamp DESC LIMIT 10;

CREATE INDEX IF NOT EXISTS conversations_timestamp_idx ON conversations (timestamp);
EXPLAIN ANALYZE SELECT * FROM conversations ORDER BY timestamp DESC LIMIT 10;
~~~

~~~text
-- sans index
Limit  (actual time=7.599..7.602 rows=10 loops=1)
  ->  Sort  (actual time=7.597..7.599 rows=10 loops=1)
        Sort Key: "timestamp" DESC
        Sort Method: top-N heapsort  Memory: 27kB
        ->  Seq Scan on conversations  (actual time=0.007..3.531 rows=50000 loops=1)
Execution Time: 7.620 ms

-- avec l'index
Limit  (actual time=0.020..0.032 rows=10 loops=1)
  ->  Index Scan Backward using conversations_timestamp_idx on conversations  (actual time=0.014..0.024 rows=10 loops=1)
Execution Time: 0.046 ms
~~~

Dans `db_init.py`, juste après le `CREATE TABLE IF NOT EXISTS conversations` :

~~~python
cur.execute("CREATE INDEX IF NOT EXISTS conversations_timestamp_idx ON conversations (timestamp)")
~~~

Sans index, Postgres lit les **50 000** lignes (`rows=50000`) pour en garder 10. Avec l'index, il le parcourt à l'envers (`Backward`) depuis la date la plus récente et s'arrête après **10** lignes. Le coût ne dépend plus de la taille de la table.
