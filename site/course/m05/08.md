@@ brief
- Les métriques disent si l'assistant est rapide et bon marché, pas s'il est **utile**. Les utilisateurs le savent : on leur donne 👍 et 👎, comme dans ChatGPT.
- Une seule table `feedback` pour tous les avis, avec une colonne `source` : `"user"` pour un humain (avec un `score`, +1 ou -1), `"judge"` pour le LLM juge de la leçon suivante (avec `relevance` et `explanation`). `conversation_id` pointe vers la conversation notée : c'est une **clé étrangère**.
- 🔑 L'`id` de la conversation doit survivre au clic : Streamlit relance tout le script, et `st.button("Ask")` vaut `False` au passage du clic sur 👍. On le range dans `st.session_state`, la mémoire de la session entre deux passages.
- Les boutons 👍 et 👎 sont au **premier niveau** du script, pas dans le `if st.button("Ask")` : sinon, au passage du clic, leur bloc ne serait même pas exécuté.
- Le signal est bruité (un clic par erreur, une mauvaise réponse notée bonne), mais il sert : une vague de 👎 dans l'heure, c'est une alerte ; et ces avis alimentent ton jeu d'évaluation.

Les deux viennent du modèle de Streamlit. Au passage du clic, `st.button("Ask")` vaut `False` : tout ce que son bloc affichait n'est plus écrit. Les boutons, eux, survivent, parce que l'`id` est dans `st.session_state`. Et chaque clic est un nouveau passage qui fait un `INSERT` de plus.

@@ practice
Corrige les deux défauts : la réponse **reste** affichée après le vote, et chaque conversation n'a **qu'un seul** avis d'utilisateur, que l'on peut changer.

@@ constraints
- Le bloc `if st.button("Ask")` calcule et enregistre, mais n'affiche rien : l'affichage se fait en dehors, à partir de `st.session_state`
- Après un clic sur +1 ou -1, la réponse, son temps et son coût sont toujours à l'écran
- Postgres lui-même garantit un seul avis `user` par conversation : un index unique, pas une vérification en Python
- Voter -1 après +1 remplace le vote (une seule ligne, score -1)
- Le juge (`source = 'judge'`) peut toujours écrire autant de lignes qu'il veut

@@ guide
### 1. Ranger le résultat

Dans le bloc Ask : `st.session_state.last = {"answer": ..., "record": ..., "conversation_id": ...}`. En dehors : `last = st.session_state.get("last")`, et si `last` n'est pas `None`, on affiche tout à partir de lui. Ainsi, chaque passage réaffiche la dernière réponse.

### 2. Un index unique partiel

`CREATE UNIQUE INDEX ... ON feedback (conversation_id) WHERE source = 'user'` : deux lignes `user` pour la même conversation deviennent impossibles, mais les lignes `judge` ne sont pas concernées. C'est un index **partiel**, grâce au `WHERE`.

### 3. Insérer ou remplacer

`INSERT ... ON CONFLICT (conversation_id) WHERE source = 'user' DO UPDATE SET score = EXCLUDED.score` : si la ligne existe déjà, Postgres la met à jour au lieu d'échouer. On appelle ça un **upsert**. `EXCLUDED` désigne la ligne qu'on essayait d'insérer.

@@ hints
- Si la réponse s'affiche deux fois juste après Ask, tu l'affiches encore dans le bloc Ask : déplace tout l'affichage en dehors.
- L'index doit être créé une fois, avec `IF NOT EXISTS` : mets-le dans `init_feedback()` ou dans une petite fonction à part.
- Le `ON CONFLICT` doit répéter le même `WHERE source = 'user'` que l'index, sinon Postgres ne trouve pas l'index correspondant.

@@ solution
`db_feedback.py`, deux fonctions de plus :

~~~python
def init_user_vote_index():
    # Un seul avis d'utilisateur par conversation. Index partiel : les lignes du juge ne sont pas concernées.
    conn = get_db_connection()
    try:
        conn.execute("""
            CREATE UNIQUE INDEX IF NOT EXISTS feedback_one_user_vote
            ON feedback (conversation_id) WHERE source = 'user'
        """)
        conn.commit()
    finally:
        conn.close()


def save_user_vote(conversation_id, score):
    timestamp = datetime.now(DB_TIMEZONE)
    conn = get_db_connection()
    try:
        conn.execute(
            """
            INSERT INTO feedback (conversation_id, source, score, timestamp)
            VALUES (%s, 'user', %s, %s)
            ON CONFLICT (conversation_id) WHERE source = 'user'
            DO UPDATE SET score = EXCLUDED.score, timestamp = EXCLUDED.timestamp
            """,
            (conversation_id, score, timestamp),
        )
        conn.commit()
    finally:
        conn.close()
~~~

`app.py` :

~~~python
import streamlit as st

from assistant import create_assistant
from db_save import save_conversation
from db_feedback import save_user_vote


@st.cache_resource
def get_assistant():
    return create_assistant()


assistant = get_assistant()

st.title("Course Assistant")

user_input = st.text_input("Enter your question:")

if st.button("Ask", disabled=not user_input.strip()):
    with st.spinner("Processing..."):
        answer = assistant.rag(user_input)
        record = assistant.last_call
        conversation_id = save_conversation(record, user_input, "llm-zoomcamp")
        # Tout ce qu'on affiche après un clic doit vivre dans session_state :
        # au prochain passage, st.button("Ask") renverra False.
        st.session_state.last = {"answer": answer, "record": record, "conversation_id": conversation_id}

last = st.session_state.get("last")

if last is not None:
    record = last["record"]
    st.write(last["answer"])
    st.write(f"Response time: {record.response_time:.2f}s")
    st.write(f"Cost: ${record.cost:.4f}")

    conversation_id = last["conversation_id"]
    col1, col2 = st.columns(2)
    with col1:
        if st.button("+1", key=f"feedback_up_{conversation_id}"):
            save_user_vote(conversation_id, 1)
            st.session_state.vote = (conversation_id, 1)
    with col2:
        if st.button("-1", key=f"feedback_down_{conversation_id}"):
            save_user_vote(conversation_id, -1)
            st.session_state.vote = (conversation_id, -1)

    vote = st.session_state.get("vote")
    if vote is not None and vote[0] == conversation_id:
        st.success(f"Ton avis est enregistré : {vote[1]:+d}. Tu peux encore changer d'avis.")
~~~

@@ breakfix
Tu as changé une colonne de `conversations` et tu veux repartir de zéro : tu lances `init_db(drop=True)`. Cette fois, la table `feedback` existe. Que se passe-t-il ?

@@ breakfix-hints
- `feedback.conversation_id` fait `REFERENCES conversations(id)`. Que deviendraient ces références si `conversations` disparaissait ?
- Lis le nom de l'erreur : il dit ce qui dépend de quoi.

@@ breakfix-answer
Postgres refuse : `psycopg.errors.DependentObjectsStillExist: cannot drop table conversations because other objects depend on it`. La clé étrangère de `feedback` dépend de `conversations` : la supprimer laisserait des avis qui pointent vers des conversations qui n'existent plus.

Deux façons de faire, à choisir **en connaissance de cause** : supprimer `feedback` d'abord, puis `conversations` ; ou `DROP TABLE conversations CASCADE`, qui supprime aussi la contrainte de `feedback`. Dans les deux cas, tu effaces des données : c'est pour ça que la leçon met en garde contre `drop=True` sur une vraie base.

@@ explain
Pourquoi vaut-il mieux que la règle « un seul vote par conversation » soit vérifiée par Postgres plutôt que par ton code Python ?

@@ cles
- st.session_state | streamlit session state | La mémoire d'une session entre deux passages du script.
- La clé étrangère | foreign key constraint postgres | Une colonne qui doit pointer vers une ligne qui existe.
- L'index unique partiel | postgres partial unique index | Une règle d'unicité qui ne vaut que pour certaines lignes.
- L'upsert | postgres insert on conflict do update | Insérer, ou mettre à jour si la ligne existe déjà.
