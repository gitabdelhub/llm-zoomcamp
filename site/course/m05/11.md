@@ brief
- Un tableau de bord avec trois conversations ne montre rien. `generate_data.py` remplit la base de **fausses conversations**, une par seconde, jusqu'à ce que tu l'arrêtes avec Ctrl + C.
- Chaque fausse conversation est un vrai `LLMCallRecord`, enregistré avec le vrai `save_conversation` : le tableau de bord ne voit pas la différence.
- 70 % reçoivent un verdict du juge (tiré au sort), 50 % un vote d'utilisateur, avec plus de 👍 que de 👎 (`[1, 1, 1, 1, -1]`).
- Une par seconde, c'est voulu : tu verras Grafana se mettre à jour presque en direct à la leçon suivante.
- 🔑 Des fausses données doivent quand même être **cohérentes** : si elles violent des règles que les vraies respectent, ton tableau de bord apprend de mauvaises habitudes, et tes tests passent sur des cas impossibles.

@@ verified
- Les fausses conversations de la leçon ne sont **pas cohérentes** : sur 30 lignes générées, **aucune** n'a `total_tokens = prompt_tokens + completion_tokens`. Les trois nombres sont tirés au sort séparément.
- Le coût est tiré au hasard lui aussi : sa corrélation avec le nombre de tokens est de **0,13** sur ces 30 lignes, alors qu'un vrai coût en dépend directement.
- Avec mon générateur corrigé (plus bas), 60 lignes sur 60 sont cohérentes, et la corrélation coût-tokens monte à **0,91**.

@@ practice
Rends le générateur **cohérent**, et ajoute un mode **incident** pour voir à quoi ressemble une panne sur le tableau de bord.

@@ constraints
- `total_tokens` est toujours la somme des deux autres
- Le coût est calculé par `calculate_cost` de `metrics.py`, à partir des tokens tirés
- `--incident` : des réponses environ 4 fois plus lentes, plus de NON_RELEVANT et une majorité de 👎
- `-n 30` génère 30 conversations sans pause puis s'arrête ; sans `-n`, une par seconde jusqu'à Ctrl + C, comme la leçon
- Une requête SQL qui compte les lignes incohérentes, et qui doit donner 0

@@ guide
### 1. Tirer d'abord, calculer ensuite

Tire `prompt_tokens` et `completion_tokens`, puis **calcule** `total_tokens` et le coût. `SimpleNamespace(input_tokens=..., output_tokens=...)` fait un faux `usage` pour `calculate_cost`.

### 2. Des tirages pondérés

`random.choices(["RELEVANT", "PARTLY_RELEVANT", "NON_RELEVANT"], weights=[3, 1, 1])[0]` tire une étiquette avec des poids. En incident, inverse les poids.

### 3. Les options

`argparse` : `parser.add_argument("--incident", action="store_true")` et `parser.add_argument("-n", type=int, default=0)`.

@@ hints
- Réutilise `SAMPLE_QUESTIONS` et `SAMPLE_ANSWERS` en les important de `generate_data.py` : inutile de les recopier.
- La requête de contrôle : `SELECT COUNT(*) FROM conversations WHERE total_tokens <> prompt_tokens + completion_tokens;`
- Pour mesurer le lien entre deux colonnes, Postgres a `corr(cost, total_tokens)`.

@@ solution
~~~python
import argparse
import random
import time
from types import SimpleNamespace

from metrics import LLMCallRecord, calculate_cost
from db_save import save_conversation
from db_feedback import save_feedback
from generate_data import SAMPLE_QUESTIONS, SAMPLE_ANSWERS

MODEL = "gpt-5.4-mini"


def fake_record(question, answer, incident=False):
    prompt_tokens = random.randint(50, 200)
    completion_tokens = random.randint(50, 300)
    usage = SimpleNamespace(input_tokens=prompt_tokens, output_tokens=completion_tokens)
    response_time = random.uniform(0.5, 5.0)
    if incident:
        response_time = response_time * 4
    return LLMCallRecord(
        model=MODEL,
        prompt=question,
        instructions="",
        answer=answer,
        prompt_tokens=prompt_tokens,
        completion_tokens=completion_tokens,
        total_tokens=prompt_tokens + completion_tokens,
        response_time=response_time,
        cost=calculate_cost(MODEL, usage),
    )


def generate_one(incident=False):
    question = random.choice(SAMPLE_QUESTIONS)
    answer = random.choice(SAMPLE_ANSWERS)
    conversation_id = save_conversation(fake_record(question, answer, incident), question, "llm-zoomcamp")
    if random.random() < 0.7:
        weights = [1, 1, 3] if incident else [3, 1, 1]
        relevance = random.choices(["RELEVANT", "PARTLY_RELEVANT", "NON_RELEVANT"], weights=weights)[0]
        save_feedback(conversation_id, "judge", relevance=relevance, explanation=f"Answer is {relevance.lower()}.")
    if random.random() < 0.5:
        score = random.choice([1, -1, -1, -1]) if incident else random.choice([1, 1, 1, 1, -1])
        save_feedback(conversation_id, "user", score=score)


if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--incident", action="store_true", help="réponses lentes et mal notées")
    parser.add_argument("-n", type=int, default=0, help="nombre de conversations (0 : sans fin)")
    args = parser.parse_args()
    i = 0
    try:
        while args.n == 0 or i < args.n:
            generate_one(args.incident)
            i += 1
            if args.n == 0:
                time.sleep(1)
    except KeyboardInterrupt:
        pass
    print(f"{i} conversation(s) générée(s)" + (" en mode incident" if args.incident else ""))
~~~

Le contrôle, après `-n 30` puis `-n 30 --incident` :

~~~sql
SELECT COUNT(*) FILTER (WHERE total_tokens <> prompt_tokens + completion_tokens) AS incoherentes,
       round(corr(cost, total_tokens)::numeric, 2) AS lien_cout_tokens,
       COUNT(*) AS total
FROM conversations;
~~~

~~~text
 incoherentes | lien_cout_tokens | total
--------------+------------------+-------
            0 |             0.91 |    60
~~~

La corrélation n'est pas de 1 : le prix d'un token de sortie est 4 fois celui d'un token d'entrée, alors que `total_tokens` les compte pareil.
