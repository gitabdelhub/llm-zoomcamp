@@ brief
- Trois conteneurs lancés à la main (Postgres, Grafana, l'application), c'est trois longues commandes à retenir. **Docker Compose** les décrit dans un seul fichier, et `docker compose up` les lance ensemble, sur un réseau commun.
- L'application Streamlit a sa propre **image**, décrite par un `Dockerfile` : Python 3.12, uv copié depuis son image officielle, les dépendances installées depuis `uv.lock` (`uv sync --locked`), puis le code.
- 🔑 Dans le Compose, chaque service trouve les autres par leur **nom de service** : l'application se connecte à `POSTGRES_HOST=postgres`, Grafana à `postgres:5432`.
- Les réglages passent par des variables d'environnement, lues dans un fichier `.env` à côté du Compose (`${POSTGRES_DB}`).
- La leçon s'arrête là, et la leçon 14 dit ce qui manque : `db_init.py` se lance encore à la main, Grafana se configure encore à la souris, rien n'attend que Postgres soit prêt. C'est le **défi** du module.

@@ guide
### 1. Le .dockerignore

Même syntaxe qu'un `.gitignore`, à la racine du contexte de build. Docker ne copie pas ce qu'il liste.

### 2. La clé sans fichier

Dans le Compose, `OPENAI_API_KEY=${OPENAI_API_KEY}` prend la valeur dans l'environnement de la commande `docker compose`. Ton secret Codespaces est déjà une variable d'environnement : rien à recopier. Le `.env` ne garde que les réglages de Postgres.

### 3. Construire et lancer

`docker compose up -d --build` reconstruit l'image puis lance tout en arrière-plan. `docker compose ps` montre l'état, `docker compose logs streamlit` les messages de l'application.

### 4. Les tables

La base du Compose est neuve : crée les tables avec `uv run python db_init.py` depuis ton Codespace, comme la leçon. Le défi fera disparaître cette étape.

@@ breakfix
Tu as écrit ton `.dockerignore`, mais seulement avec `.env`. L'image se construit, puis le conteneur s'arrête aussitôt, et `docker compose logs streamlit` affiche `exec /app/.venv/bin/streamlit: no such file or directory`. Le fichier existe pourtant bien dans le dossier. Pourquoi ?

@@ breakfix-hints
- Que fait `COPY . .` d'un dossier `.venv` qui existe sur ton Codespace ?
- Un environnement virtuel contient des liens vers l'interpréteur Python qui l'a créé. Où est cet interpréteur ?

@@ breakfix-answer
`COPY . .` a copié ton `.venv` du Codespace **par-dessus** celui que `uv sync` avait construit dans l'image. Le script `/app/.venv/bin/streamlit` existe, mais sa première ligne (le *shebang*) pointe vers le Python de ton Codespace, qui n'existe pas dans le conteneur. Le système dit alors « no such file or directory », en parlant de l'interpréteur, pas du script.

Ajoute `.venv` au `.dockerignore` et reconstruis. Règle générale : une image se construit à partir du **code** et du **fichier de verrouillage**, jamais à partir de l'environnement d'une autre machine.

@@ explain
Ton `.gitignore` contient déjà `.env`. Pourquoi faut-il en plus un `.dockerignore` ?

@@ cles
- Le .dockerignore | dockerignore file build context | Ce qui ne doit pas entrer dans l'image, comme un .gitignore pour Docker.
- Le contexte de build | docker build context | Le dossier que Docker envoie au build, et que COPY peut copier.
- Les noms de service | docker compose service name networking | Dans un Compose, un service en trouve un autre par son nom.
- Les secrets dans une image | docker image secrets leak | Une clé copiée dans une image se lit par quiconque a l'image.
