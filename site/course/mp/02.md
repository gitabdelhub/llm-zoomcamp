- Chaque morceau de texte a un **identifiant stable** : le même document doit garder le même `id` d'une ingestion à l'autre, sinon ta vérité terrain ne veut plus rien dire.
- 🔑 L'ingestion doit pouvoir être **relancée** sans doublons : c'est ce qui la rend automatisable.

@@ predict
Ton DAG d'ingestion découpe 20 notices en morceaux et les insère dans Postgres. Tu le lances deux fois de suite. Combien de lignes as-tu, et que devient ton hit rate ?

@@ predict-answer
Le double, si tu fais de simples `INSERT`. Chaque passage existe deux fois avec deux lignes différentes : la recherche rend deux fois le même texte dans le top 5, ce qui pousse d'autres bons passages dehors. Si les `id` sont générés au hasard (`uuid4`), ta vérité terrain pointe vers les `id` de la première ingestion seulement. Un `id` calculé à partir du contenu (un hash du document et du numéro de morceau) et un `INSERT ... ON CONFLICT DO NOTHING` rendent la seconde ingestion sans effet.

@@ practice
Construis l'ingestion et le premier flux RAG de ton projet.

@@ constraints
- Un pipeline d'ingestion lancé par un outil (un DAG Airflow ou un pipeline dlt), qui télécharge le corpus, le découpe et le charge dans la base
- Des `id` stables, calculés à partir du contenu, et une ingestion relancée deux fois sans doublon
- Une fonction `rag(question)` : recherche, prompt, LLM, et la liste des `id` des passages utilisés dans sa sortie
- Un test qui vérifie qu'une ingestion relancée ne change pas le nombre de lignes

@@ guide
### 1. Découper

Pour des PDF, extrais le texte page par page, puis coupe en morceaux de 300 à 500 mots avec un léger chevauchement. Garde le document et la page dans chaque morceau : tu en auras besoin pour citer tes sources.

### 2. Identifier

`hashlib.sha256(f"{doc_id}:{chunk_index}:{text}".encode()).hexdigest()[:16]` : le même morceau donne toujours le même `id`.

### 3. Charger

Une table avec une clé primaire sur `id`, et `ON CONFLICT (id) DO NOTHING`. Avec dlt, `write_disposition="merge"` et une `primary_key`.

### 4. Le flux

Reprends le RAG du module 1, avec ton gabarit de prompt. Fais rendre à `rag` les `id` des passages : tu en as besoin pour l'évaluation et le monitoring.

@@ hints
- Si tu changes la taille des morceaux, les `id` changent aussi : c'est normal, mais il faut régénérer la vérité terrain après.
- Dans Airflow, une tâche qui télécharge et une qui charge : si le chargement échoue, tu relances seulement lui.
- `SELECT id, count(*) FROM chunks GROUP BY id HAVING count(*) > 1` doit rendre zéro ligne.

@@ solution
Sur l'exemple des jeux de société, un découpage avec des `id` stables :

~~~python
import hashlib


def chunk_pages(doc_id, pages, size=400, overlap=50):
    words = [(page_no, w) for page_no, text in enumerate(pages, start=1) for w in text.split()]
    chunks, start, index = [], 0, 0
    while start < len(words):
        part = words[start : start + size]
        text = " ".join(w for _, w in part)
        chunks.append({
            "id": hashlib.sha256(f"{doc_id}:{index}:{text}".encode()).hexdigest()[:16],
            "doc_id": doc_id,
            "page": part[0][0],
            "text": text,
        })
        start, index = start + size - overlap, index + 1
    return chunks
~~~

Et le chargement qu'on peut relancer :

~~~sql
CREATE TABLE IF NOT EXISTS chunks (
    id TEXT PRIMARY KEY,
    doc_id TEXT NOT NULL,
    page INTEGER NOT NULL,
    text TEXT NOT NULL,
    embedding vector(384)
);

INSERT INTO chunks (id, doc_id, page, text, embedding)
VALUES (%s, %s, %s, %s, %s)
ON CONFLICT (id) DO NOTHING;
~~~
