@@ brief
- La source **`filesystem`** liste les fichiers qui correspondent à un motif (`**/*.jsonl`) ; le lecteur **`read_jsonl`** ouvre chacun et renvoie ses lignes. dlt les relie avec l'opérateur **`|`**, comme une commande shell.
- 🔑 dlt **normalise** : il déduit les types, aplatit les objets imbriqués (`message.usage.output_tokens` devient la colonne `message__usage__output_tokens`) et met **chaque liste dans une table enfant**, reliée à sa ligne parente par `_dlt_id` et `_dlt_parent_id`.
- Avec des logs d'agent, très imbriqués, ça donne vite des dizaines de tables : 78 dans le workshop. C'est correct, mais inutilisable. La leçon 3 corrige ça.
- `dev_mode=True` ajoute un horodatage au nom du dataset à chaque run (un dataset neuf à chaque fois) ; `write_disposition="replace"` vide et recharge la table. Pratique pour développer, à retirer ensuite.
- La pipeline du dossier `code/` fait un autre choix : elle garde **chaque ligne brute** dans une colonne `data`, plus quelques champs utiles (`agent`, `session_id`, `type`, `timestamp`), dans une seule table `log_records`.

@@ solution
`naive_pipeline.py` :

~~~python
"""La pipeline de la leçon : chaque ligne JSON telle quelle, et dlt déroule tout."""
from pathlib import Path

import dlt
from dlt.sources.filesystem import filesystem, read_jsonl

reader = (
    filesystem(bucket_url=f"file://{Path.home()}/.zlaude", file_glob="projects/**/*.jsonl")
    | read_jsonl()
).with_name("messages")

pipeline = dlt.pipeline(
    pipeline_name="naive_logs",
    destination="duckdb",
    dataset_name="agent_logs",
    dev_mode=True,
)
pipeline.run(reader, write_disposition="replace")

tables = sorted(pipeline.default_schema.data_table_names())
print(len(tables), "tables :", tables)
~~~

Sur les logs fictifs, avec dlt 1.32, elle affiche `12 tables`, de `messages` à `messages__tool_use_result__structured_patch__lines`.

Pour la pipeline officielle, une seule ligne change, dans `load()` :

~~~python
destination=dlt.destinations.duckdb("agent_logs_store.duckdb"),
~~~

au lieu de `destination="duckdb"`. Le chargement complet passe alors : `log_records: 907 row(s)` sur les logs fictifs.

@@ breakfix-hints
- Dans DuckDB, un fichier de base est un **catalogue**, et un dataset de dlt est un **schéma** dans ce catalogue. Comment s'appelle le fichier que dlt crée, par défaut ?
- Compare `pipeline_name` et `dataset_name` dans `load()`.
- Que fait `dev_mode=True` au nom du dataset, et quand est-il activé dans ce fichier ?

@@ breakfix-answer
Par défaut, dlt nomme le fichier DuckDB d'après la pipeline : `agent_logs.duckdb`. DuckDB en fait un **catalogue** nommé `agent_logs`. Le dataset s'appelle aussi `agent_logs` : c'est un **schéma** du même nom. Quand dlt écrit `agent_logs.log_records`, DuckDB ne sait pas si `agent_logs` désigne le catalogue ou le schéma, et refuse.

`--sample` passait parce qu'il active `dev_mode=True`, qui renomme le dataset en `agent_logs_20261116…` : plus de conflit. Le piège n'apparaît donc qu'au moment où l'on passe en vrai chargement.

La réparation : donner au fichier un autre nom, avec `destination=dlt.destinations.duckdb("agent_logs_store.duckdb")`. C'est exactement le nom qu'attend le tableau de bord officiel de la leçon 3, dont un commentaire explique ce conflit. Changer `dataset_name` marche aussi, mais le tableau de bord ne trouverait plus ses tables.

@@ cles
- La normalisation de dlt | dlt normalizer nested data child tables | Comment dlt transforme du JSON imbriqué en tables reliées.

- La source filesystem de dlt | dlt filesystem source read_jsonl | Lire des fichiers locaux ou dans un bucket, avec un motif.
