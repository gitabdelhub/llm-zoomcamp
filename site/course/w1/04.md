@@ brief
- En entreprise, les logs des agents ne sont pas sur ton disque : ils sont dans un service de suivi (Logfire, Langfuse, Datadog), derrière une **API REST**. Chaque service a son propre format, et dlt normalise tout de la même façon.
- Le workshop utilise une API de test : un million de traces fictives de Claude Code, sans authentification, avec la même structure que les vraies.
- La source **`rest_api`** se décrit par un dictionnaire : l'URL de base, le **paginateur**, et les ressources. `data_selector: "logs"` dit que les lignes sont sous la clé `logs` de la réponse. Le paginateur **`offset`** envoie `limit` et `offset`, et lit le total dans `total` pour savoir quand s'arrêter.
- 🔑 `maximum_offset` arrête la pagination plus tôt (20 000 lignes au lieu d'un million), sans boucle à écrire. La leçon en parle, mais le code du dossier `code/` ne l'a pas : il utilise `add_limit(1)` pour une seule page.
- L'objet `usage`, au premier niveau des traces de l'API, devient des colonnes `usage__output_tokens` ; la liste `message.content` devient la table enfant `logs__message__content`.

@@ verified
L'API de test est bloquée depuis mon environnement. J'ai testé le code officiel contre une copie locale de son format (`/logs?limit=&offset=`, réponse `{"logs": [...], "total": ...}`), avec dlt 1.32 :
- `add_limit(1)` fait **1** requête et charge 1 000 lignes ; `maximum_offset=3000` fait **3** requêtes et charge 3 000 lignes.
- Le code incrémental de la leçon 7 (`"incremental": dlt.sources.incremental("index")` dans la ressource) est **refusé** par dlt 1.32 : `DictValidationException`. La forme acceptée se met dans `endpoint` : `"incremental": {"cursor_path": "index", "initial_value": 0}`.
- Avec cette forme, sur 5 000 lignes : le premier run fait 5 requêtes et charge 5 000 lignes ; le deuxième, sans rien de nouveau, fait **encore 5 requêtes** et charge 0 ligne.
- `RUNTIME__LOG_LEVEL=INFO` affiche une ligne `Making GET request to ...` par requête : c'est comme ça qu'on les compte.

@@ practice
Fais de la pipeline officielle une pipeline qu'on peut relancer chaque jour : limitée à 20 000 lignes, sans doublons, et dont tu connais le coût en requêtes.

- La ressource `logs` en `merge`, avec la clé `index` et un incrémental sur `index`
- Deux lancements de suite : tu as compté les requêtes de chacun et les lignes chargées

@@ guide
### 1. Le premier lancement

Copie `cohorts/2026/workshops/dlt/code/rest_api_pipeline.py` et lance-le une fois tel quel : une page, 1 000 lignes. Regarde les tables avec `uv run dlthub local show` ou `pipeline.dataset()`.

### 2. 20 000 lignes

Dans le dictionnaire `paginator`, ajoute `"maximum_offset": 20000`. Retire `add_limit(1)` du mode normal.

### 3. Relancer sans doublons

`"write_disposition": "merge"` dans `resource_defaults`. Dans l'`endpoint` de `logs` : `"incremental": {"cursor_path": "index", "initial_value": 0}`. Ne mets pas `dlt.sources.incremental(...)` directement dans la ressource, comme à la leçon 7 : dlt 1.32 refuse cette forme.

### 4. Compter

~~~bash

~~~

Lance-le deux fois. Compare.

@@ hints
- Si le deuxième run charge 20 000 lignes de nouveau et que ta table en a 40 000, le `merge` n'a pas de clé : vérifie `primary_key: "index"`.
- L'incrémental de dlt **filtre les lignes après les avoir reçues**. Pour économiser des requêtes, il faut que l'API accepte un paramètre de filtre. Ouvre la page `/docs` de l'API de test : si `/logs` accepte un paramètre comme `since` ou `min_index`, `start_param` dans la configuration `incremental` l'envoie à chaque run.
- `pipeline.last_trace.last_normalize_info` montre le nombre de lignes de chaque table pour le dernier run.
- Le paginateur `offset` a besoin de `total_path` : sans lui, il ne sait pas où s'arrêter.

@@ solution
La source modifiée :

~~~python
@dlt.source(name="agent_logs_api")
def agent_logs_source(base_url: str = dlt.config.value, page_size: int = 1000, maximum_offset: int | None = 20000):
    paginator = {
        "type": "offset",
        "limit": page_size,
        "offset": 0,
        "limit_param": "limit",
        "offset_param": "offset",
        "total_path": "total",
    }
    if maximum_offset:
        paginator["maximum_offset"] = maximum_offset
    config: RESTAPIConfig = {
        "client": {"base_url": base_url, "paginator": paginator},
        "resource_defaults": {"write_disposition": "merge"},
        "resources": [
            {
                "name": "logs",
                "endpoint": {
                    "path": "/logs",
                    "data_selector": "logs",
                    "incremental": {"cursor_path": "index", "initial_value": 0},
                },
                "primary_key": "index",
            },
        ],
    }
    yield from rest_api_resources(config)


def load(full: bool = False) -> None:
    pipeline = dlt.pipeline(pipeline_name="agent_traces", destination="duckdb", dataset_name="traces")
    source = agent_logs_source(base_url=BASE_URL, maximum_offset=None if full else 20000)
    info = pipeline.run(source)
    print(info)
    print(pipeline.last_trace.last_normalize_info)
~~~

Ce que tu devrais mesurer : 20 requêtes et 20 000 lignes au premier run ; 20 requêtes et 0 ligne au second. Sur ma copie locale de l'API, avec 5 000 lignes, le premier run faisait 5 requêtes, le second encore 5 pour 0 ligne, et après l'ajout de 1 000 lignes, 6 requêtes pour les 1 000 nouvelles : le filtre se fait **chez toi**. Avec `--full`, un million de lignes, chaque run relit mille pages, même pour zéro ligne nouvelle. Le `merge` protège la table ; il ne protège pas l'API.

@@ cles
- La source REST API de dlt | dlt rest_api source declarative config | Décrire une API par un dictionnaire au lieu d'écrire des boucles.
- La pagination par offset | offset limit pagination total | Avancer de page en page avec limit et offset, et savoir quand s'arrêter.
- Le chargement incrémental | dlt incremental cursor start_param | Ne charger que le nouveau, et quand il faut que l'API filtre elle-même.
- Les spécifications OpenAPI | OpenAPI specification /docs endpoint | La description d'une API qu'un agent lit pour écrire la pipeline.
