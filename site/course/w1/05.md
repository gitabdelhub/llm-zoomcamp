@@ brief
- Un tableau de bord local ne se partage pas. La **plateforme dltHub** fait tourner tes pipelines et tes notebooks dans le cloud, les planifie, et les partage avec ton équipe.
- Le cycle : `uv run dlthub login` (une connexion par le navigateur), `uv run dlthub workspace connect`, puis **`dlthub deploy`** (envoyer le code) et **`dlthub run`** (lancer). On recommence après chaque changement de code.
- 🔑 Une pipeline vers `duckdb` qui tourne dans le cloud écrit dans un **stockage éphémère** : le conteneur disparaît à la fin du job, et les données avec. Pour les garder, on change de destination : **`playground`**, un lac de données géré (sur S3), qui a besoin du paquet `deltalake`.
- Le même code de pipeline, avec une autre chaîne de destination : c'est tout l'intérêt de dlt.

@@ declic
- [DE:01-04] Au Zoomcamp DE, une base Postgres dans un conteneur sans volume perdait ses données à chaque arrêt. Le stockage éphémère de la plateforme, c'est la même leçon, à l'échelle d'un job.

@@ codespaces
- `dlthub login` affiche un code et une adresse : ouvre l'adresse dans ton navigateur et entre le code. Dans un Codespace, c'est ce mode « appareil » qui marche, car le terminal n'a pas de navigateur.
- Le compte est gratuit. Ne mets aucun secret dans `.dlt/config.toml` : il est versionné. Les secrets vont dans `.dlt/secrets.toml`, que le `.gitignore` de `dlthub-init` exclut déjà.

@@ explain
Pourquoi une pipeline qui marche en local peut-elle « perdre » ses données une fois déployée ? Qu'est-ce qui change, et qu'est-ce qui ne change pas, quand tu passes de `duckdb` à `playground` ?

@@ cles
- Le stockage éphémère | ephemeral storage container jobs | Ce qu'un conteneur écrit disparaît avec lui.
- Les destinations de dlt | dlt destinations filesystem delta lake | Changer où vont les données sans changer la pipeline.
- Delta Lake | delta lake table format | Le format de tables d'un lac de données, avec un historique des versions.
