@@ brief
- `__deployment__.py` est le **manifeste** du déploiement : il liste les jobs de la plateforme. Une pipeline y devient un job **batch** ; un notebook marimo importé (`from agent_traces_dashboard import app`) devient un job **interactif**.
- 🔑 Un notebook déployé doit dire **où** lire : `dlt.attach("agent_traces", destination="playground", dataset_name="agent_logs")`. En local, dlt retrouve la destination dans l'état de la pipeline ; dans le cloud, cet état n'existe pas.
- Le notebook s'ouvre en **mode run** : le code est caché, on ne voit que les graphiques. `dlthub job publish` donne une adresse publique.
- La planification s'écrit dans un décorateur : `@run.pipeline("agent_traces", trigger=trigger.schedule("0 12 * * *"))`, une expression cron. Un déclencheur `job.success` enchaîne les jobs : la pipeline, puis le tableau de bord.

@@ declic
- [DE:02-08] Au Zoomcamp DE, tu as écrit des expressions cron pour Airflow. `0 12 * * *` se lit pareil : tous les jours à 12 h 00, en UTC.
- [03-05] Le déclencheur `job.success` ressemble aux assets d'Airflow 3 : lancer un job quand un autre a fini, plutôt qu'à une heure fixe.

@@ explain
Pourquoi `dlt.attach` a-t-il besoin de `destination` et `dataset_name` dans le cloud, alors qu'il s'en passe en local ? Que gagne-t-on à enchaîner le tableau de bord sur le succès de la pipeline, plutôt qu'à le planifier une heure plus tard ?

@@ cles
- Les expressions cron | cron expression syntax | Dire « tous les jours à midi » en cinq champs.
- L'enchaînement de jobs | event driven job triggers on success | Lancer un job quand un autre a réussi.
- Partager un notebook | marimo app run mode share | Un notebook qui devient une application, code caché.
